# 专辑/艺人分页 IPC 队列延迟调查（结案报告）

> **日期**：2026-09-20
> **分支**：`perf/disable-artist-album-images` → 已 fast-forward 合入 main（`370e311` 修复 + `e539070` 本报告）；图片禁用实验已回退（图片无辜）
> **过程复盘**：调查全程时间线与三轮误判分析见 `专辑艺人分页IPC延迟调查时间线复盘_2026-09-20.md`
> **现象**：专辑/艺人网格分页加载时，`http://ipc.localhost/library_get_albums` / `library_get_artists` 在 DevTools Network 面板显示 Queueing（队列等待）2s 以上，实测最高 7985ms；页面翻页明显卡顿
> **规模背景**：真实曲库 32,466 首歌 / 3,838 张专辑 / 1,893 位艺人；专辑分页 30 张/页，响应体 196-334KB（含 base64 内联封面缩略图）

---

## 一、结论（TL;DR）

**根因：Chromium（WebView2）的请求调度器在滚动动画活动期间扣住渲染器新发起的网络请求，优先保滚动流畅。** 一次 `invoke` 的真实时间拆解：

```
⏳ 前端发出 invoke（0-1ms，渲染器立即创建请求）
       ↓
⏳ Chromium ResourceScheduler 扣住请求不放     ←←← 5.6~8 秒全在这
   （检测到滚动动画/惯性进行中，延迟新请求启动）
       ↓
放行：OPTIONS 预检 2-10ms → POST 到达 Rust（ENTER）→ 后端 1.5-3.2ms
       ↓
响应回传 ~90ms（300KB body）→ 前端收到
```

- **后端无辜**：ENTER→EXIT 仅 1.5-3.2ms
- **wry/IPC 管道无辜**：请求一旦放行，全链路 ~130ms
- **图片无辜**：禁用网格图片后照样慢（最初的假设被证伪）
- **DevTools 无辜**：关闭 DevTools 后照样慢（第二个被证伪的假设）
- **前端渲染无辜**：`console.log` → 请求创建仅 0-1ms

**“为什么前端看起来慢、后端却非常快”**：慢的不是我们的任何一层代码，而是请求在浏览器进程里**根本没有被放行**——DevTools 的 Queueing 显示的就是这段调度器扣留时间。

## 二、测量方法：三视角时间戳对齐

在 WebView2 里同时拿三个独立时钟的数据，逐请求对齐：

| 视角 | 数据来源 | 含义 |
|---|---|---|
| T1 前端发出 | 页面 console 时间戳（`src/utils/tauriInvoke.ts` AOP 包装的 ⏩/✅ 日志） | 渲染器 JS 创建 fetch 的时刻 |
| T2 网络层 | CDP `Network.requestWillBeSent`（`wallTime` 纪元秒 / `timestamp` 单调秒） | 各请求进入各自 instrumentation 的时刻（见 §5 陷阱） |
| T3 后端 | `src-tauri/src/ipc_trace.rs` 的 ENTER/EXIT 日志（本地时间毫秒） | 命令真正进入 Rust 的时刻 |

**CDP 接入方式**：`tauri.conf.json` → `windows[0].additionalBrowserArgs: "--remote-debugging-port=9223"`（环境变量 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` 方式实测无效），node-repl + `ws` 包连 `ws://127.0.0.1:9223/devtools/page/<id>`，`Network.enable` + `Runtime.enable` 持续采集。

**决定性线索——两种 requestId 时钟不同源**：

- POST 的 `requestWillBeSent` requestId 形如 `5548.201`——**渲染器侧**发出，时刻 = fetch 创建（不是真实上线）
- OPTIONS 预检的 requestId 是 32 位 hex——**网络服务侧**发出，时刻 = 真实上线

两者之差就是调度器扣留时间。

## 三、证据链与控制变量实验

### 3.1 用户会话对齐（图片已禁用，DevTools 开着，物理滚轮）

8 次专辑分页，POST 创建 → 后端 ENTER 的间隔 vs 前端 AOP 总耗时：

| # | POST 创建 | Rust ENTER | 扣留 | AOP 总耗时 |
|---|---|---|---|---|
| 1 | 06:05:47.512 | 47.515 | **3ms** | 41ms |
| 2 | 47.946 | 49.728 | **1782ms** | 1794ms |
| 3 | 50.564 | 55.065 | **4501ms** | 4517ms |
| 4 | 06:06:00.305 | 06:06:02.463 | **2158ms** | 2246ms |
| 5 | 03.564 | 07.882 | **4318ms** | 4415ms |
| 6 | 13.240 | 16.949 | **3709ms** | 3805ms |
| 7 | 20.415 | 24.685 | **4270ms** | 4363ms |
| 8 | 30.922 | 36.495 | **5573ms** | 5668ms |

扣留时间与 AOP 总耗时逐条吻合（差值 = 响应回程 ~10-100ms）。第 1 条只要 3ms——管道空闲时完全畅通。

**铁证**：请求 #8 的后端 ENTER（36.495）恰好等于其 OPTIONS 预检的网络响应时刻（36.495）——OPTIONS 响应后几毫秒 POST 就进了 Rust。**放行后一切飞快，秒级延迟全部在放行之前**。

### 3.2 管道拥塞时 OPTIONS 与 POST 的待遇差异

同一拥塞窗口内（wallTime 换算，同一秒轴）：

| 请求 | 发出 | 响应 | 往返 |
|---|---|---|---|
| OPTIONS `90AD…` | 322.364 | 322.371 | **7ms** |
| POST #1（被扣中） | 316.850 创建 | 322.445 才回 | 5595ms |
| OPTIONS `A87B…` | 330.323 | 330.327 | **4ms** |
| OPTIONS `E2C5…` | 345.137 | 345.142 | **5ms** |

预检由网络服务直接发起（不经过渲染器调度队列），**7ms 穿越同一管道并超车被扣 5 秒的 POST**——证明不是整条管道堵，是渲染器的新请求被定向压制。空闲时的同类 POST（`plugin:window|minimize`）22ms 往返。

### 3.3 决定性控制变量实验（同一实例、同一份 360-390 卡片 DOM）

| 触发下一页的方式 | 滚动动画 | invoke 实测 |
|---|---|---|
| `scrollBy({behavior:'instant'})` 程序化瞬时滚动 | 无 | **132ms** |
| `scrollBy({behavior:'smooth'})` 程序化平滑滚动 | 有 | **7985ms**（请求创建后 7.9s 才放行） |
| 用户物理滚轮连续快滚 | 有（Windows 平滑滚动+惯性） | 5598-6727ms |
| 空闲时触发（启动首页 / 最小化） | 无 | 22-37ms |

**触发器是滚动动画状态本身**（程序化 smooth 也复现，排除 OS 输入管线因素），不是 DOM 大小（两种滚动 DOM 相同）、不是图片、不是 DevTools、不是 Tauri 任何一层。

### 3.4 用户操作模式为何必然踩中

无限滚动交互 = 「新页渲染 → 快速滚完 ~1300px 到底 → IntersectionObserver(400px margin) 触发下一页」。请求**恰好**在滚动突发刚结束、惯性/动画尚未退去的时刻创建，正面落进调度器的扣留窗口；且 330+ 张无虚拟化卡片的渲染压力拉长了 busy 状态的释放时间（放行滞后动画结束可达数秒）。

## 四、被证伪的中间假设（避坑记录）

1. **“图片加载阻塞 IPC 队列”**（最初的第三方 AI 诊断 + 我们的洪泛实验背书）：200 并发冷 artwork 请求确实能让 IPC 劣化 100 倍（当时判定"根因确认"），但用户慢速场景里**管道中一个 artwork 请求都没有**（CDP 全量记录证实），禁用图片后照样慢。洪泛实验结论本身成立，只是不是用户场景的主因。
2. **“DevTools 是 20-30 倍放大因子”**：我 CDP 无头驱动 ~147ms vs 用户开 DevTools 1.8-5.6s，曾归因 DevTools UI 开销。**关闭 DevTools 后实测 5598-6727ms，更慢了**——假设作废。真正差异是驱动滚动的强度（见 3.3）。
3. **“wry/Rust 分发层排队”**：对齐表一度显示「POST→ENTER 数秒」被解读为 wry 管道排队——实际是 OPTIONS/POST 时钟源不同（§2/§5），POST 创建到真实上线之间管道根本还没收到请求。wry 实测 2-10ms。

## 五、CDP + WebView2 测量陷阱（可复用经验）

1. **自定义协议无完成事件**：CDP 对 `ipc.localhost` / `lumo.localhost` 这类 WebView2 自定义协议**不报送 `responseReceived` / `loadingFinished` 的可靠完成事件**，只有 `requestWillBeSent`——不要把"没收到完成事件"误判为"请求挂起"。用 `img.complete` 或页面侧计时交叉验证。
2. **requestWillBeSent 的语义分两种时钟源**：渲染器侧事件（requestId `frameId.nnn`）= fetch **创建**时刻；网络服务侧事件（32 位 hex requestId，典型是 CORS 预检）= **真实上线**时刻。两者之差 = 调度器扣留。**前端 console 与渲染器网络事件对齐只能证明"渲染器没卡"，不能证明"请求及时上线"。**
3. **时钟域**：`wallTime` 是纪元秒、`timestamp` 是单调秒、`Runtime.consoleAPICalled.ts` 是纪元毫秒。换算：单调秒 + 固定偏移（本会话实测偏移 1789866472.040，用 sent 事件的 `wallTime - ts` 校验恒定性后再套用）。
4. **每次 Tauri invoke = OPTIONS 预检 + POST 两个请求**（CORS，预检缓存 TTL ~10s）；慢请求的 OPTIONS 出现在「放行瞬间」而不是 fetch 创建时——分析时不要把它当成"孤儿预检"。
5. 调试端口写法：`tauri.conf.json` → `additionalBrowserArgs`，环境变量方式无效。

## 六、修复方向（按性价比排序）

1. **`--disable-smooth-scrolling`**（`tauri.conf.json` additionalBrowserArgs，一行）：轮滚变瞬时步进、无动画 → 调度器没有扣请求的理由。**✅ 已验证（2026-09-20，同 §3.3 场景对照）**：`scrollBy(smooth)` 触发分页 7985ms → **116ms**（69 倍）；瞬时滚动连续翻页 47-93ms/页；动画探测 `animated:false`（Blink 平滑滚动确认关闭）。代价是滚动手感变离散（体验取向见 §8）。
2. **预取时机（应用层正解思路）**：让下一页请求在用户滚动突发**开始之前**发出（如前页渲染完成后延时预取下一页），绕开扣留窗口。注意：rootMargin 直接加大到 > 单页内容高度（~1300px）会导致不进滚也连环预加载整个库，需用「距底部百分比/页面高度阈值」或"用户确实在滚动"的信号做门控。若不接受修复 1 的滚动手感，改走本方案。
3. **网格虚拟化**：长期正解。390 卡片 / 16k px 滚动区的渲染压力拉长 busy 释放时间，也影响流畅度与内存。
4. **响应瘦身**：`library_get_albums` 响应去掉 base64 `cover_thumbnail_base64`（300KB → ~20KB），把无扣留延迟从 ~130ms 压到 ~20ms，并降低放行后的 JSON 解析主线程压力。

## 八、补充观察

- **CDP 合成滚轮事件（`Input.dispatchMouseEvent` mouseWheel）不复现扣留**（突发 12 tick 实测 137ms）——它不经过浏览器的轮子平滑滚动动画管线，进一步佐证触发器是滚动动画而非滚轮事件本身。
- flag 生效后 `behavior:'smooth'` 的程序化平滑滚动同样退化为瞬时跳位（同一 Blink 开关门控），文档/代码里如依赖平滑滚动动效需注意。
