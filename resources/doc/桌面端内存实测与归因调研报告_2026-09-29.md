# Lumo 桌面端内存实测与归因调研报告

> 日期：2026-09-29
> 依据：[桌面端内存治理方案_2026-09-29.md](桌面端内存治理方案_2026-09-29.md) 阶段 A（测量 → 定位）
> 数据来源：本机实测采样 CSV + 曲库只读取证 + 代码审计
> 性质：基于实测的调研报告；下方附有后续执行记录。本报告中的内存收益仍须通过同口径 A/B 测量确认。

---

## 0. 结论摘要

1. **Rust 侧可以排除**：主进程（数据库/扫描/播放核心）全程稳定在 38→53 MiB，无增长、无泄漏迹象。整组内存的波动几乎全部来自 WebView2 进程组。
2. **静置状态下不是 700 MB**：本机 dev 构建静置基线为整组 ≈ 246 MiB。用户观察到的约 700 MB 是**活动期**数字——实测活动期峰值 878 MiB、稳态 ≈ 480–550 MiB。
3. **最大的、可确定的浪费是"解码尺寸不当"**：曲库封面中位 640×640、p90 1500px、最大 5795px。一张 5795px 封面解码为 RGBA 需要 **127 MiB**，而它在界面上出现的位置（底部播放栏 48px、Inspector 220px）只需要 200px 缩略图（**160 KiB**）。数据库里已经存好了 200px 缩略图（3150 张全部就绪，均值 10 KB），但小尺寸展示位仍在请求原图。
4. **专辑网格的累积是第二大头**：3819 张专辑在无限滚动时全量累积在 store 中，每张附带约 13.7 KB 的 base64 缩略图字符串（合计可达 ~52 MiB 的 JS 字符串），且解码后的 200×200 位图（160 KiB/张，全量上界 611 MiB）由 Chromium 图片缓存承载。
5. **尚不能证明存在内存泄漏**：renderer 呈锯齿（GC 型）而非单调增长；方案要求的"60 分钟防回弹"判据本次未测。
6. **本次数据不能保证 100 MiB 目标**：本机 dev 静置时 GPU 92 + renderer 71 + browser 36 ≈ 200 MiB，但一次 dev 测量不能证明架构的不可降低下限。应先做 release 多次对照；若治理后仍达不到硬指标，再进入阶段 E（原生样机）。此处结论于 2026-09-30 修正。

**读法**：
- **GPU 是弹性变量**（116 ↔ 469 MiB），随滚动增长、空闲后自行回落——这是缓存（栅格瓦片 + 图片纹理）行为，不是泄漏。
- **renderer 呈锯齿**（55 → 310 → 180 → 210），符合 V8 GC 周期 + 部分保留，也不是典型泄漏曲线。
- **main 极其稳定**（38 → 53 后恒定不变），Rust 侧无增长。
- 全段斜率（末 25%）：整组 +27 MiB/分钟、renderer +28 MiB/分钟、GPU −1.1、main 0.0。renderer 的正斜率需要 60 分钟长跑才能判定是"缓存未满期的正常爬升"还是"缓慢泄漏"。

## 4. 归因分析（分层，标注证据强度）

### 4.1 【已证实·代码审计】小槽位请求原图，且缺少尺寸变体

`getArtworkUrl()`（`src/utils.ts:36`）只生成单一大小的 URL；`lumo://artwork/<id>` 协议处理器（`src-tauri/src/lib.rs:349` 起）**只返回原图文件**（`artwork.cache_path`），没有尺寸参数。DB 里已有的 `thumbnail_blob`（200×200）仅通过专辑/歌单 DTO 的 base64 内联字段下发。

使用原图的小尺寸展示位（`useArtworkSrc` 调用点，均为常驻组件）：

| 位置 | 显示尺寸 | 每张解码（本机曲库分布） |
|---|---|---|
| `BottomPlayer.vue:15` 底栏封面 | 48 px | 中位 1.6 MiB，p90 8.6，p99 36.7，**最大 127** |
| `SidebarRight.vue:19` Inspector 封面 | ≤220 px | 同上 |
| `AlbumDetail.vue:47` / `PlaylistDetail.vue:37` 详情头图 | 152 px | 同上 |
| `NowPlayingImmersive.vue:28` 沉浸页 | 大图（合理） | 同上（此处置合理） |
| `ArtistGrid.vue:232` 头像 | 180 px | 仅 11 位艺人有头像，实际影响小 |
| `MobileLayout.vue:82` 等移动端 | 小图 | 同上（Android 另测） |

**放大效应**：Windows 下 `useArtworkSrc` 会 `fetch()` 同一 URL 并转 data URL 入缓存 → 同一张原图可能被**解码两次**（`http://…` 一次、`data:` 一次），并且 base64 字符串常驻 JS 堆。以 p99 封面为例：36.7 MiB × 2 + 48 MiB 字符串 ≈ **120 MiB 只为显示一张 48 px 的底栏封面**。

**可确定的收益**：小槽位改用 200px 缩略图后，单张解码从（中位 1.6 MiB / p99 36.7 MiB）降到 160 KiB，即 **10×–800× 的降幅**，视觉上在 48–220 px 槽位无可感知差异。

### 4.2 【已证实·代码审计 + DB 计数】专辑网格全量累积

`player.ts` 的 `fetchAlbums(false)` 执行 `albums.value = [...albums.value, ...newAlbums]`（`player.ts:1241`），`AlbumGrid.vue:150` 到底部即续拉；每张专辑对象携带 `cover_thumb`（`player.ts:1234`，来自 `cover_thumbnail_base64`）。

- 3819 张专辑全部滚完 → **base64 字符串约 52 MiB** 常驻 JS 堆（V8 对 ASCII 字符串可能按 1 B/char 存，最坏 2 B/char → 最高 ~105 MiB）。
- 解码后的 200×200 位图 160 KiB/张，全量上界 **611 MiB**，由 Chromium 图片缓存承载（受其内部策略淘汰，实际介于数十至数百 MiB）。
- 网格本身**未虚拟化**（普通 CSS grid，DOM 节点随加载量线性增长）。

### 4.3 【已证实·实测】Rust 侧稳定，可排除为主因

main 进程 38 MiB（静置）→ 53 MiB（活动后）后**恒定不变**，三次独立观测方差 < 1 MiB。C 阶段已把连接池页缓存理论上限从 ~768 MiB 收敛到 96 MiB，实测未观察到主进程波动。扫描场景（S5）未测，扫描期峰值仍属未知。

### 4.4 【尚未知·需实验】以下项目有嫌疑但无实测证据

| 嫌疑 | 为什么尚未知 | 验证方式（下一轮） |
|---|---|---|
| 三处常驻 `backdrop-blur`（TopBar md / BottomPlayer xl / SidebarRight 2xl） | 模糊需要合成器保留背板纹理并随滚动重算，但未做开关对照 | 加运行时开关做 A/B（见 §6-E2） |
| 底栏 32 根 `will-change: transform` 波形条持续动画 | 每个 `will-change` 元素通常获得独立合成层，播放大半场持续动画 | 播放中对比开/关波形 |
| V8 堆无上限（未设 `--js-flags=--max-old-space-size`） | renderer 锯齿 180↔310 提示 GC 时机主导，未做上限对照 | 追加 browser 参数做 A/B（§6-E3） |
| Chromium 栅格瓦片缓存 | 专辑网格 3819 卡片使可滚动高度极大，栅格瓦片随滚动生成 | 虚拟化前后对照（§6-E4） |
| 是否存在真实泄漏 | 需 60 分钟稳态判据 | 60 分钟长跑（§6-E5） |
| WebView2 内存级别控制（`SetMemoryUsageTargetLevel`） | wry 0.55 已实现 `set_memory_usage_level`，但 **Tauri 2.11.2 未透出该 API**（已核对源码） | 需要 COM 互操作或等上游；S6 后台场景暂无法用此手段 |

**工具侧待办**（不影响结论，但影响下一轮数据质量）：

2. 每 30 s 落一次 summary，避免"关窗口无汇总"。
3. 增加活动标记能力（如控制台 `__LUMO_MEM__.mark('开始滚动')`），把操作与内存曲线对齐——否则归因只能靠推断。
4. 补诊断计数：`document` 节点数、`<img>` 数、store 持有的 base64 总字节。

## 9. 执行记录：E1 缩略图按需加载（2026-09-29）

根据 E1 优先项，已在代码中增加缩略图协议变体：小尺寸封面默认请求 `?size=thumb`，后端直接返回数据库中已生成的 200×200 JPEG；没有缩略图的旧数据仍回退到原图。沉浸式播放大封面和系统媒体通知明确请求原图。前端 data URL 缓存键包含 artwork ID 与尺寸，防止缩略图/原图互相串用；Windows 预取只缓存缩略图，避免把原图再复制进 JS 堆。

## 11. 执行记录：缩小渲染窗口与释放异步资源（2026-09-30）

### 已实施

- **桌面、移动端专辑和艺人网格统一虚拟渲染**：只挂载可见行及上下各一行缓冲，分页提前加载距离从 400px 缩到 150px。随容器宽度计算列数和行高，覆盖视口底部半行；缩短列表后钳制旧滚动位置，避免空白。
- **艺人每页 50→30 条**：启动 bundle 与后续分页一致；艺人状态使用浅层响应式，头像更新通过替换数组触发渲染。已加载的轻量元数据仍保留，以支持返回时恢复滚动；这不是 store 数据页淘汰。
- **单一图片通道**：列表使用现有 200×200 JPEG 缩略图协议 URL。移除 Windows 下额外 fetch→Base64 转换及其队列；不再让同一封面在 JS 侧保存一份长期图片字符串。旧 LRU 模块保留兼容清理接口，当前封面通道不再写入它。浏览器仍自行管理图片缓存，不能保证离屏即释放解码内存。
- **旧图回退不长期缓存**：缺少缩略图时暂时回退原图的响应设为 `no-store`，避免后台补齐缩略图后，浏览器仍把原图长期缓存在同一缩略图 URL。
- **取色与系统媒体通知使用缩略图**：沉浸页大封面仍请求原图；取色任务切换或卸载时取消，清空图片回调，取色结束把 canvas 尺寸归零。
- **合并刷新**：专辑和艺人分页各自最多一个请求在途。请求过程中发生多次重置，只继续执行最新筛选，旧响应不能覆盖新列表或分页位置；移动端艺人补齐分页观察器。
- **页面资源清理**：卸载取消待处理滚动帧、断开观察器并停止匹配任务继续派发；清理匹配完成计时器。已发送的后端匹配请求仍可能完成。移动端重新进入网格时重建对应滚动根的观察器。
- **测量修正**：环境登记新增工作区 dirty 状态、运行程序路径/SHA256/修改时间；采样等待扣除 CIM 查询开销，汇总记录有效平均间隔，同类多进程先按时间点相加再算分位数。dev 前端仍需结合操作记录确认加载的代码；二进制指纹不能单独代表热更新前端。
