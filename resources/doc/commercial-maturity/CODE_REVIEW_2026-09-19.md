## 3. 阻断问题

### CR-001：失败恢复副本会在下一次恢复时被覆盖

- 严重度：P1
- 位置：`src-tauri/src/commands/sync.rs:169-198`
- 影响范围：数据库云端恢复、自动回滚失败后的人工救援
- 触发条件：
  1. 云端快照通过校验；
  2. 恢复 live 数据库失败；
  3. 自动回滚同样失败；
  4. 用户再次点击恢复。

当前逻辑在恢复失败时保留固定名称的 `lumo.sqlite.restore_bak`，并明确提示该文件可能是用户唯一的历史数据。但下一次恢复开始时，会无条件删除这个固定名称文件，再从可能已经处于半恢复状态的 live 数据库创建新副本。因此第二次操作可能永久销毁唯一可人工恢复的数据。

建议整改：

1. 回滚副本使用带时间戳或随机标识的唯一文件名；
2. 启动恢复前检查是否存在未处理的救援副本；
3. 存在救援副本时禁止静默覆盖，向用户提供“打开位置、另存、确认丢弃”等明确选项；
4. 只在恢复成功且数据库重新校验通过后清理本轮副本；
5. 为“恢复失败且回滚失败，再次恢复”增加自动化测试。

验收标准：

- 连续执行任意次数失败恢复，都不会覆盖已有救援副本；
- 错误提示中的路径对应一个实际存在且可独立打开的 SQLite 文件；
- 救援副本的删除必须由成功流程或用户明确操作触发；
- 测试能够模拟 restore 与 rollback 同时失败的分支。

## 4. 高优先级问题

### CR-002：自动切歌的“重试”会改为播放下一首

- 严重度：P2
- 位置：`src-tauri/src/commands/queue.rs:432-466`
- 影响范围：WebDAV 网络抖动、文件暂时不可用、自动切歌

`internal_play_item` 在真正解析和打开媒体文件之前就更新 `q.index`。第一次播放下一首失败后，退避结束时观察者重新调用 `q.next_index()`，此时得到的已经是再下一首，而不是刚刚失败的曲目。连续失败计数也会把不同曲目的错误视为同一组失败，只向前端发送第一条错误。

建议整改：

1. 保存本次失败的目标索引，在退避期间只重试该索引；
2. 或者把 `q.index = index` 延后到播放器成功接受媒体源之后；
3. 失败去重至少应以 `track_id/media_file_id + 错误类别` 为键；
4. 用户手动切歌、替换队列或停止播放时必须清空旧退避状态；
5. 增加“第二首失败、第三首可用”的队列测试，确认第二首不会被错误跳过。

验收标准：

- 同一曲目发生瞬时失败时，重试目标保持不变；
- 不同曲目的失败不会被错误合并；
- 用户操作可以立即打断自动重试；
- 恢复成功后失败计数和下一次尝试时间全部清零。

### CR-003：校验和上传失败会遗留完整远端暂存文件

- 严重度：P2
- 位置：`src-tauri/src/services/sync.rs:422-439`
- 影响范围：WebDAV 配额、重复备份、远端数据治理

数据库暂存文件上传成功后，如果 `lumo.sqlite.sha256` 上传失败，`?` 会直接结束闭包。清理逻辑只覆盖 MOVE 失败分支，不覆盖校验和失败及其他提前返回路径。由于暂存名称每次都不同，重复失败会持续留下完整数据库副本并消耗远端空间。

建议整改：

1. 为远端暂存文件增加作用域清理守卫；
2. 只有 MOVE 成功后才解除守卫；
3. 任意中间步骤失败时执行 best-effort DELETE，并同时记录删除失败；
4. 上传开始前可清理超过安全期限的本应用暂存文件；
5. 使用可控 WebDAV 测试服务模拟 checksum PUT 失败并验证无残留。

验收标准：

- 校验和上传、MOVE、网络断开任一失败后，不留下新的长期暂存文件；
- 清理失败时错误信息包含远端暂存对象名称；
- 不会误删其他客户端仍在上传的暂存对象。

### CR-004：快照上传会同时持有两份完整数据库

- 严重度：P2
- 位置：`src-tauri/src/services/sync.rs:407-431`
- 影响范围：大型曲库备份、低内存设备、桌面进程稳定性

快照先被完整读入 `Vec<u8>`，上传暂存文件时又调用 `data.clone()`。正常成功路径也会同时保留原数据和克隆数据。对于数百 MiB 至数 GiB 的数据库，这会显著增加内存峰值，并可能导致进程被操作系统终止。

建议整改：

1. WebDAV PUT 改为从 `File` 或受控分块流读取；
2. MOVE 不可用时重新打开快照文件进行第二次上传，不在内存中保留备用副本；
3. 为快照增加明确的本地大小上限与用户提示；
4. 性能基线记录 100 MiB、500 MiB、1 GiB 快照的峰值内存；
5. 上传过程支持进度与取消，避免用户把长耗时误认为卡死。

验收标准：

- 峰值额外内存不随快照大小线性增长到两倍；
- 1 GiB 快照可以在常见 8 GiB 内存设备上稳定完成；
- MOVE 降级路径不依赖内存中的第二份数据。

### CR-005：缓存状态查询会污染 LRU 使用时间

- 严重度：P2
- 位置：`src-tauri/src/services/cache.rs:112-146`
- 影响范围：音频缓存淘汰、离线可用性、磁盘命中率

`is_cached()` 直接调用 `get_cached_path()`，后者会刷新缓存文件的 mtime。批量可播性查询和 `playback_is_cached` 都属于只读状态检查，但它们同样会把缓存标记成“刚刚使用”。打开歌曲列表可能一次刷新大量缓存，最终淘汰顺序反映列表查询顺序，而不是真实播放历史。

建议整改：

1. 拆分 `validate_cached_path` 与 `acquire_cached_path`；
2. 前者只校验存在性和大小，不更新 mtime；
3. 只有实际进入播放路径时才更新时间；
4. 如需更可靠的商业实现，使用独立索引存储 `last_access_at`，避免依赖文件系统 mtime；
5. 增加测试，证明调用 `is_cached` 不改变淘汰顺序。

验收标准：

- 查询歌曲可播性不会更新缓存访问时间；
- 实际播放缓存文件会更新访问时间；
- 淘汰测试能够保留近期真实播放的文件。

### CR-006：WebDAV 扫描早退没有落库失败原因

- 严重度：P2
- 位置：`src-tauri/src/commands/scanner.rs:315-331`
- 影响范围：凭据失效、数据库连接失败、扫描状态反馈

WebDAV 凭据解析失败或扫描线程无法取得数据库连接时，代码只记录日志并发送 `scan-complete`，没有更新 `sources.last_error`。前端现在收到完成事件后会重新读取数据库状态，因此用户只能看到旧时间或旧错误，无法知道本次扫描为何失败。

建议整改：

1. 建立统一的扫描终止函数，负责落库状态、发送事件和记录日志；
2. 所有扫描启动后的早退路径必须经过该函数；
3. `scan-complete` 事件增加结构化结果，例如 `success/error_code/message`；
4. 数据库本身不可用时，事件中仍需携带临时错误，供前端直接展示；
5. 增加凭据失效与连接池耗尽测试。

验收标准：

- 凭据失效后，桌面端和移动端都能显示明确错误；
- 每个已启动的扫描最终都会产生成功或失败终态；
- 不存在前端永久停留在“扫描中”的早退路径。

### CR-007：大文件传输缺少可终止的应用层超时

- 严重度：P2
- 位置：`src-tauri/src/services/webdav.rs:32-63,423-430`
- 影响范围：整文件缓存、数据库快照上传、前端操作状态

`bulk_client` 仅配置连接超时，不设置总超时，并用 TCP keepalive 作为挂死连接兜底。TCP keepalive 只能探测失联的 TCP 对端，不能处理“连接仍存活、仍响应 ACK，但应用层不再发送或读取数据”的服务器。此时阻塞请求可能长时间不返回，前端会持续停留在备份或缓存状态。

建议整改：

1. 为大文件传输定义较高的总时间预算；
2. 增加“连续若干秒无字节进展”的空闲超时；
3. 向上传递取消令牌，允许用户主动终止；
4. 对上传和下载分别设置合理阈值，不共用同一个粗粒度策略；
5. 使用故障服务器模拟连接建立后不再传输数据。

验收标准：

- 服务器停滞时，请求能在明确时间内返回可理解错误；
- 慢速但持续有进展的大文件传输不会被误杀；
- 前端最终一定退出“处理中”状态；
- 用户取消后不留下本地或远端半成品。

### CR-008：联网登记门禁无法证明新增外联已登记

- 严重度：P2
- 位置：`scripts/check-network-registry.mjs:39-55`
- 影响范围：隐私承诺、外联变更治理、CI 可信度

当前脚本只扫描 Rust 源码中的硬编码 `http(s)://` 字符串，并按文件路径判断文档是否已登记。一个文件只要曾经登记过，在其中增加新的外联域名仍会通过；由配置、变量或字符串拼接生成的 AI、WebDAV 等目标也不会被识别。因此 CI 通过只能说明部分文件名出现在文档中，不能证明“所有新增外联都已登记”。

建议整改：

1. 建立结构化联网清单，为每个外联行为分配稳定 ID；
2. 网络调用封装层必须声明对应行为 ID；
3. CI 校验调用点引用的 ID 均存在、清单中无悬空条目；
4. 对前端 `fetch/window.open` 和 Rust `reqwest` 同时覆盖；
5. 如果暂时保留当前脚本，应把 CI 名称和说明改为“硬编码 URL 文件登记检查”，避免过度承诺。

验收标准：

- 在已登记文件里新增一个域名但不更新清单时，CI 必须失败；
- 新增动态 URL 网络调用但不声明行为 ID 时，CI 必须失败；
- 前端与 Rust 后端使用同一套联网行为事实源。

### 9.1 CR-008 的实现口径

- **事实源仍是本文件的 §1 表 + §2 小节**，没有另建 JSON 清单：§1 同时是给用户看的对外承诺，
  另起一份结构化清单必然与它漂移。机器可读性靠固定的表格列与 `### X.` 标题约定达成。
- 三条验收标准对应的判定：①代码行里的字面量主机逐个比对 §1（M1/M7 变异证明）；
  ②HTTP 客户端动词调用与构造点、前端 `fetch` / `window.open` / `WebSocket` 等调用点必须带
  `// 联网行为: §2X`，一个标记只服务一个调用点，跨行链式调用会被折叠后照样判定（M2/M3/M5/M6 证明）；
  ③前后端调用 `scanFile` 时传同一份 registry 对象。
- 当前全仓 **35 处调用点全部带声明**；`lumo://` 本地协议显式声明 `联网行为: local`，
  回环与保留域（`127.x`、`localhost`、`::1`、`*.local`、`example.*`）与 Rust `#[cfg(test)]` 段豁免。
- 顺手如实登记的两项：`github.com`（发布页跳转，原 §1 G 行只写了 `api.github.com`）；
  MA0 Spike 的 `debug_webdav_probe` 新增 §1 H 行 + §2H 小节，其「release 二进制仍注册该命令」
  记为 §4 R-10（P2，转 I2 收口）。

### 9.2 CR-008 残余缺口（必须如实说）

1. 判定靠模式匹配：接收者名字不含 `client` 的裸调用、经第三方封装库发出的请求、
   以及把 URL 拼进非字面量再调用的写法，仍可能漏判。它证明的是「按约定写的调用点都跑了声明」，
   不是「不存在未声明的外联」。
2. §1 中「由响应决定的动态主机」（网易云 CDN、`mzstatic.com`）无法穷举，清单里出现而代码里没有时
   只打印告警，不做硬失败——否则门禁会拒绝诚实的文档写法。
3. `#[cfg(test)]` 只在顶格时整段豁免；写在函数内部的 `cfg(test)` 块不豁免（宁可多判不误放）。
4. 前端现已扫描 TS/JS 可执行代码及 Vue `<script>` 内的全部 URL 字面量；Vue 模板不扫描，
   因而地址输入框 placeholder 不会误报。若未来在模板表达式里直接发起外联，仍需扩展解析规则。
