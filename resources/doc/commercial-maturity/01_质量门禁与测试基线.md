# I1：质量门禁与测试基线

> 优先级：P0  
> 建议周期：7–10 个工程日  
> 建议容量：34 点 Committed，5 点 Stretch  
> 前置：I0 产品契约与 Stable 范围已确认  
> 迭代目标：让每次变更都能自动证明“可构建、核心行为未回退、发布输入可重复”。

## 1. 当前问题

- 前端没有单元、组件或 E2E 测试脚本；
- Rust 仅有 9 个单元测试，未覆盖数据库迁移、扫描和恢复等高风险链路；
- `cargo fmt --check` 与 `cargo clippy --all-targets -- -D warnings` 失败；
- 只有 tag 发布工作流，没有 PR 质量门禁；
- 发布使用 `npm install`，依赖安装不可完全复现；
- 核心状态和命令文件过大，改动容易产生跨功能回归。

## 2. 成功标准

- 所有 PR 必须通过统一 CI；
- 主分支格式和严格静态检查为零错误；
- 核心数据、播放、扫描、备份恢复至少具备 happy path 与失败路径测试；
- 前端具备 Store/组件测试和最小启动 E2E；
- tag 发布只消费已经通过验证的提交；
- 测试失败能明确指出责任模块，而不是只返回“构建失败”。

## 3. 用户故事与估算

| ID | 用户故事 | 优先级 | 点数 |
|---|---|---:|---:|
| QA-001 | 作为维护者，我需要 PR 自动门禁，以便问题不能直接进入主分支 | Critical | 5 |
| QA-002 | 作为开发者，我需要清零格式和静态检查债务，以便后续只处理新增问题 | Critical | 5 |
| QA-003 | 作为用户，我需要数据库升级后数据保持完整，以便放心更新软件 | Critical | 8 |
| QA-004 | 作为用户，我需要扫描和播放核心行为可回归，以便版本升级不破坏曲库 | High | 8 |
| QA-005 | 作为发布者，我需要最小端到端冒烟，以便证明安装后能够完成核心任务 | High | 5 |
| QA-006 | 作为团队，我需要可读的测试报告和质量趋势，以便判断是否可发布 | Medium | 3 |

## 4. 详细执行点

### QA-001：PR 持续集成

- [ ] 新增 `.github/workflows/ci.yml`；
- [ ] 前端固定 Node 与 npm 版本并使用 `npm ci`；
- [ ] 运行 TypeScript 检查与 Vite 生产构建；
- [ ] 运行前端测试；
- [ ] Rust 固定 stable 工具链版本或建立升级窗口；
- [ ] 运行 `cargo fmt --check`；
- [ ] 运行 `cargo clippy --all-targets -- -D warnings`；
- [ ] 运行 `cargo test --all-targets`；
- [ ] 检查 package、Cargo、Tauri、Android 版本一致；
- [ ] 对 Windows、macOS、Linux 做最小编译矩阵；
- [ ] CI 取消重复旧任务，避免浪费资源；
- [ ] 设置主分支保护，要求 CI、评审和最新基线；
- [ ] 发布工作流只允许在 CI 已通过的 tag 上运行。

验收标准：

```text
Given PR 引入 TypeScript 错误、Rust 告警或失败测试
When CI 执行
Then PR 不允许合并，并能定位失败步骤

Given 合法 PR 全部检查通过
When 合并到 main
Then main 状态为绿色，并可作为发布候选输入
```

### QA-002：清零现有工程债务

- [ ] 运行格式化并单独提交纯格式变化；
- [ ] 分类处理 Clippy 问题：正确性、性能、可维护性、纯风格；
- [ ] 不通过大范围 `allow` 掩盖问题；
- [ ] 对确需豁免项写明原因、作用范围和复审日期；
- [ ] 删除无效导入、死代码和重复工具函数；
- [ ] 为超大模块建立拆分方案，但本迭代只做降低测试难度所需拆分；
- [ ] 建立提交前本地检查命令；
- [ ] 确保 Windows 与 CI 环境换行符一致。

### QA-003：数据库迁移回归

- [ ] 保存至少 v1.1.1、v1.3.0、v1.8.0 三个匿名化数据库 fixture；
- [ ] 为全新建库建立 schema 快照测试；
- [ ] 对每个历史 fixture 执行升级；
- [ ] 验证 `schema_migrations` 顺序、唯一性和幂等；
- [ ] 验证歌曲、专辑、艺术家、歌单、收藏、播放历史数量；
- [ ] 验证升级后 `PRAGMA integrity_check`；
- [ ] 重复启动并确保迁移不会再次破坏数据；
- [ ] 注入中途失败，验证原库仍可恢复；
- [ ] 建立迁移耗时上限和大库测试口径；
- [ ] 禁止在没有 fixture 测试的情况下增加新迁移。

验收标准：

```text
Given 任一受支持历史数据库
When 升级到当前版本
Then 完整性检查通过，核心实体数量符合预期，重复启动结果不变

Given 迁移过程被故意中断
When 应用再次启动
Then 不使用半迁移状态继续运行，并给出可恢复错误
```

### QA-004：核心后端回归

- [ ] 队列四种播放模式保留现有测试并补边界；
- [ ] 增加空队列、单曲队列、删除当前曲目、恢复队列测试；
- [ ] 为本地扫描建立临时目录 fixture；
- [ ] 覆盖新增、修改、删除、不可访问目录和损坏音频；
- [ ] 验证扫描失败不会错误标记整库 missing；
- [ ] 为 WebDAV 建立可控 mock server；
- [ ] 覆盖 Range 206、忽略 Range 返回 200、认证失败、超时和错误 Content-Range；
- [ ] 为快照上传、校验、恢复、回滚建立测试；
- [ ] 覆盖凭据缺失、重新认证和旧数据迁移；
- [ ] 确保测试不访问真实互联网。

### QA-005：前端与 E2E 基线

- [ ] 选定前端测试框架并写入 ADR；
- [ ] 为 player、ui、sync、ai Store 建立最小单元测试；
- [ ] 为隐私开关验证默认关闭与持久化；
- [ ] 为错误态、空态、加载态建立组件测试；
- [ ] 建立 IPC mock 层，避免前端测试依赖真实 Tauri；
- [ ] 建立最小 E2E：启动、添加测试来源、扫描、浏览、播放、退出；
- [ ] 增加离线启动冒烟；
- [ ] 增加升级后首次启动冒烟；
- [ ] E2E 失败保留截图、日志和测试数据。

### QA-006：质量报告

- [ ] CI 上传测试结果和构建日志；
- [ ] 记录测试数量、失败率和耗时趋势；
- [ ] 建立 flaky test 定义和隔离规则；
- [ ] 不以覆盖率作为唯一目标，但对核心模块设置最低基线；
- [ ] 发布评审展示未覆盖高风险清单；
- [ ] 生成可追溯到提交 SHA 的质量摘要。

## 5. 建议测试分层

| 层级 | 目标 | 重点 |
|---|---|---|
| 单元测试 | 快速验证纯逻辑 | 队列、路径、优先级、加解密封装、解析器 |
| Repository 测试 | 验证 SQL 与迁移 | CRUD、约束、事务、统计字段 |
| Service 集成测试 | 验证模块协作 | 扫描、缓存、WebDAV、恢复 |
| 前端 Store/组件 | 验证状态与交互 | 隐私开关、错误态、队列、设置 |
| E2E 冒烟 | 验证可交付主链路 | 安装后导入、浏览、播放、重启 |
| 平台人工矩阵 | 验证系统集成 | 媒体键、后台播放、音频焦点、签名安装 |

## 6. 风险与应对

| 风险 | 应对 |
|---|---|
| 一次性修复格式产生巨大 diff | 独立提交，不混入行为修改 |
| 测试依赖真实音乐与私有库 | 建立小型合法/自生成 fixture |
| 音频与系统 API 难以自动测试 | 核心逻辑抽象后单测，系统部分保留人工矩阵 |
| CI 时间过长 | PR 跑快速集，夜间跑完整兼容集 |
| 为追求覆盖率写无价值测试 | 按数据损失与用户影响优先，不追求表面百分比 |

## 7. 退出清单

- [ ] PR CI 已启用并为合并必需；
- [ ] 格式和严格 Clippy 全绿；
- [ ] 前端测试脚本存在且 CI 执行；
- [ ] 三个历史数据库 fixture 升级成功；
- [ ] 扫描、播放、WebDAV、恢复具备核心回归；
- [ ] 最小 E2E 可重复运行；
- [ ] 发布工作流不再绕过质量门禁；
- [ ] 所有失败测试都有明确错误输出和证据。
