# I4：签名、更新与发布工程

> 优先级：P0  
> 建议周期：7–10 个工程日  
> 建议容量：32 点 Committed，5 点 Stretch  
> 前置：I1 CI 全绿，I2 安全门禁，I3 数据升级与回滚验证  
> 迭代目标：让用户能够验证安装包来源，并能安全完成安装、升级、失败回滚和版本追溯。

## 1. 成功标准

- Windows、macOS、Android 的正式产物都能验证发布者身份；
- 每个发布产物都关联 commit、版本、校验和和 SBOM；
- Beta 与 Stable 使用不同发布规则，不会误发；
- 升级保留数据，失败后有明确回滚路径；
- 发布工作流不可绕过质量、安全和数据门禁；
- 完成一次成功发布演练和一次失败回滚演练。

## 2. 用户故事与估算

| ID | 用户故事 | 优先级 | 点数 |
|---|---|---:|---:|
| REL-001 | 作为 Windows 用户，我希望安装包有可信签名，以便降低 SmartScreen 风险 | Critical | 5 |
| REL-002 | 作为 macOS 用户，我希望应用已签名并公证，以便可以正常安装运行 | Critical | 5 |
| REL-003 | 作为 Android 用户，我希望 APK 签名和版本连续，以便安全覆盖升级 | Critical | 3 |
| REL-004 | 作为用户，我希望更新失败时保留原版本和数据 | Critical | 8 |
| REL-005 | 作为发布者，我需要可重复发布与产物证明，以便审计每个版本 | High | 5 |
| REL-006 | 作为维护者，我需要发布演练和回滚手册，以便紧急情况下可执行 | High | 3 |
| REL-007 | 作为用户，我希望知道当前版本状态和支持范围 | Medium | 3 |

## 3. 详细执行点

### REL-001：Windows 可信发行

- [ ] 选择合适的代码签名证书类型和保管方案；
- [ ] 私钥不进入仓库和普通 CI 日志；
- [ ] 为 MSI、NSIS/EXE 和主程序签名；
- [ ] 配置可信时间戳服务；
- [ ] CI 验证签名、证书链、时间戳和文件哈希；
- [ ] 在干净 Windows 10/11 环境测试安装、覆盖升级、卸载；
- [ ] 验证卸载不删除用户音乐，是否保留应用数据有明确选择；
- [ ] 记录 WebView2 安装和离线环境行为；
- [ ] 发布页标注架构与最低系统版本。

### REL-002：macOS 签名与公证

- [ ] 配置 Developer ID Application 证书；
- [ ] 确认 universal binary 同时包含 x86_64 与 arm64；
- [ ] 配置 hardened runtime 与所需 entitlement；
- [ ] 对 `.app` 完成深度签名验证；
- [ ] 上传 Apple notarization 并 staple ticket；
- [ ] 使用 Gatekeeper 验证下载后的 DMG；
- [ ] 在 Intel 与 Apple Silicon 至少各完成一次安装与播放；
- [ ] 测试应用数据目录、系统钥匙串和媒体权限；
- [ ] 记录最低 macOS 版本，不以构建成功代替功能支持。

### REL-003：Android 签名与升级连续性

- [ ] 将 keystore 做双份离线备份并记录恢复步骤；
- [ ] CI 构建后执行 `apksigner verify --verbose`；
- [ ] 验证 APK 实际 ABI 与文件名一致；
- [ ] 确认 versionCode 单调递增且由单一版本源生成；
- [ ] 测试旧 Stable 到新 Stable 覆盖升级；
- [ ] 测试权限变化、数据库迁移、后台服务和通知；
- [ ] 构建后清理临时 keystore 和 properties；
- [ ] 为未来商店签名迁移保留决策记录。

### REL-004：升级、降级与回滚

- [ ] 明确支持自动更新、手动更新或仅通知策略；
- [ ] 更新元数据必须签名并走 HTTPS；
- [ ] 更新前检查目标版本、平台、架构和最低系统要求；
- [ ] 更新前生成数据库恢复点；
- [ ] 数据库迁移成功前不得删除旧恢复点；
- [ ] 更新失败保留当前可运行版本；
- [ ] 禁止默认静默降级到旧 schema 客户端；
- [ ] 如允许降级，必须明确数据兼容范围；
- [ ] 对下载中断、哈希错误、签名错误、磁盘满进行故障注入；
- [ ] 设置页展示当前通道、版本、检查时间和更新结果；
- [ ] 更新检查失败不能提示“已是最新”；
- [ ] 建立紧急撤回更新元数据的流程。

验收标准：

```text
Given 更新包签名或哈希不匹配
When 客户端验证更新
Then 更新被拒绝，当前版本和数据保持可用

Given 新版本数据库迁移失败
When 用户重新启动应用
Then 可以恢复到升级前数据，并收到明确说明
```

### REL-005：可重复发布流水线

- [ ] 只允许从受保护主分支的签名 tag 发布；
- [ ] 发布前检查工作区版本、tag 与 changelog 一致；
- [ ] 使用锁文件和固定工具版本；
- [ ] 所有发布 job 依赖统一的 verify job；
- [ ] 生成 SHA256SUMS，尽可能对校验文件签名；
- [ ] 上传 SBOM、第三方 Notice 和质量摘要；
- [ ] 产物命名包含产品、版本、平台、架构；
- [ ] Release Notes 包含变化、已知问题、数据迁移和回滚说明；
- [ ] 构建产物保留策略满足问题追溯；
- [ ] 发布完成后自动验证下载链接与文件大小；
- [ ] 发布失败不得留下看似完整的 Stable Release。

### REL-006：发布与回滚手册

- [ ] 建立 T-3 天候选冻结；
- [ ] 建立发布前检查、发布中监控、发布后冒烟步骤；
- [ ] 定义发布负责人和第二复核人；
- [ ] 定义停止发布和撤回条件；
- [ ] 定义热修复版本规则；
- [ ] 演练错误签名、错误版本号、数据库迁移失败、第三方服务故障；
- [ ] 记录演练时间、执行者、结果和改进项。

### REL-007：用户可见版本信息

- [ ] 关于页展示版本、通道、提交或构建号；
- [ ] 提供 Release Notes、隐私政策、安全说明入口；
- [ ] 明确 Stable/Beta/Experimental 含义；
- [ ] 显示当前平台支持限制；
- [ ] 诊断包自动包含上述信息，但不含敏感数据。

## 4. 发布产物要求

| 产物 | 必须项 |
|---|---|
| Windows MSI/EXE | 代码签名、时间戳、SHA256、安装/升级冒烟 |
| macOS DMG/App | Developer ID、公证、staple、Universal 验证 |
| Linux AppImage/deb/rpm | SHA256、依赖说明、发行版兼容矩阵 |
| Android APK | release 签名、apksigner 验证、versionCode、ABI 验证 |
| 全平台 | SBOM、Release Notes、已知问题、commit SHA |

## 5. 风险与应对

| 风险 | 应对 |
|---|---|
| 证书成本或申请周期影响进度 | 先完成流程和测试证书演练，Stable 等正式证书就绪 |
| 自动更新扩大攻击面 | 在签名、CSP、回滚未完成前保持手动更新 |
| 跨平台构建结果不一致 | 统一版本源与验证脚本，保留平台专项冒烟 |
| 错误 tag 自动公开不完整 Release | 先草稿、全产物验证后再发布 |
| Android keystore 丢失 | 离线双备份与年度恢复演练 |

## 6. 退出清单

- [ ] Windows 正式产物签名验证通过；
- [ ] macOS 签名与公证验证通过；
- [ ] Android 签名、版本和 ABI 验证通过；
- [ ] 所有产物都有校验和、SBOM 和提交信息；
- [ ] 安装、覆盖升级、卸载矩阵完成；
- [ ] 更新失败与数据迁移失败回滚通过；
- [ ] 发布和回滚手册经过实际演练；
- [ ] Release 不可绕过 I1–I3 门禁。
