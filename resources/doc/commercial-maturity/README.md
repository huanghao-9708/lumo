# Lumo 商业成熟化迭代总计划

> 文档状态：Draft v1  
> 规划基线：Lumo v1.8.1  
> 默认资源假设：1 名熟悉 Vue、Rust、SQLite、Tauri 与 Android 的全栈开发者  
> 规划目的：在不扩张新功能的前提下，将 Lumo 从“功能型 Beta”推进为“可稳定交付、可被信任、可持续维护”的软件产品。

## 1. 结论与总目标

Lumo 当前已经具备完整播放器、WebDAV、Android、AI 电台和跨平台发行能力。接下来的主要矛盾不是功能不足，而是产品承诺、质量证据、安全机制、发布信任和用户运营尚未形成闭环。

本计划冻结非必要新功能，集中完成以下七个迭代：

1. 统一产品契约与发布语义；
2. 建立持续质量门禁；
3. 补齐安全、隐私与供应链治理；
4. 建立数据可靠性与 WebDAV 兼容性证据；
5. 建立签名、升级、回滚和跨平台发布体系；
6. 建立用户支持、诊断和文档体系；
7. 通过外部 Beta 验证完成 Stable 发布决策。

最终目标不是“任务全部勾选”，而是能够回答并证明：

- 每次提交是否安全、可构建、可回归；
- 用户数据是否可恢复、可迁移、不会因异常扫描或升级损坏；
- 所有联网行为是否经过用户授权并与隐私声明一致；
- 安装包是否来自可信发布者，升级失败是否可回退；
- 用户遇到问题时是否能够自助解决或提供可用诊断；
- Stable 版本是否经过真实外部用户验证。

## 2. 范围边界

### 2.1 本计划包含

- 产品定位、联网边界、功能状态与术语统一；
- CI、自动化测试、质量门禁和版本治理；
- CSP、凭据保护、依赖审计、SBOM 和安全响应；
- 数据库迁移、备份恢复、扫描一致性与 WebDAV 兼容性；
- Windows/macOS/Android 签名、发布、更新与回滚；
- 日志、诊断包、FAQ、支持流程和用户文档；
- Beta 用户验证、成功指标、商业路径与 Stable Go/No-Go。

### 2.2 本计划不包含

- 新增播放格式、均衡器、社交、歌词编辑等功能；
- 扩展新的 AI 模式或推荐算法；
- 开发真正的实体级多端合并同步；
- 大规模视觉重做；
- 在质量基线建立前进行性能微优化；
- 未经验证的商店上架投入。

任何新需求必须先进入商业成熟化 Backlog，不得直接插入当前迭代。只有 P0 缺陷、数据损坏、安全漏洞和构建阻断可以中断迭代。

## 3. 当前基线

| 维度 | 当前状态 | 本计划目标 |
|---|---|---|
| 前端构建 | `npm run build` 通过 | PR 与发布均自动验证 |
| Rust 测试 | 9 个单元测试 | 覆盖核心数据、扫描、播放、同步与迁移链路 |
| 前端测试 | 无测试脚本 | 单元/组件测试 + 最小 E2E 冒烟 |
| 格式与静态检查 | `cargo fmt --check`、严格 Clippy 不通过 | 主分支零错误，禁止新增告警 |
| CI | 仅 tag 发布工作流 | PR CI、夜间兼容检查、受保护主分支 |
| 依赖安全 | npm 审计存在高危传递依赖 | 高危为零或有书面豁免与截止日期 |
| 凭据安全 | 桌面部分走系统钥匙串，部分平台仍为 XOR 混淆 | 平台安全存储 + 认证加密 + 迁移测试 |
| 桌面签名 | 未形成完整可信链 | Windows 签名、macOS 签名与公证 |
| 同步语义 | 整库快照上传/恢复 | 对外准确命名为备份恢复，并有完整防损测试 |
| 支持能力 | 无正式支持与安全政策 | 用户文档、诊断包、支持分级和响应流程 |
| 用户验证 | 主要由作者真实曲库验证 | 10–20 位外部 Beta 用户、连续两周验证 |

## 4. 迭代总览

| 迭代 | 名称 | 建议周期 | 主要产出 | 前置依赖 | 发布阻断 |
|---|---|---:|---|---|---|
| I0 | 产品契约与范围冻结 | 3–5 天 | Product Charter、真实功能矩阵、版本与联网政策 | 无 | 是 |
| I1 | 质量门禁与测试基线 | 7–10 天 | PR CI、测试分层、核心回归、分支保护 | I0 | 是 |
| I2 | 安全隐私与供应链治理 | 7–10 天 | 威胁模型、凭据升级、CSP、隐私政策、SBOM | I0、I1 | 是 |
| I3 | 数据可靠性与 WebDAV 兼容性 | 7–10 天 | 迁移/恢复测试、扫描一致性、兼容矩阵 | I1 | 是 |
| I4 | 签名更新与发布工程 | 7–10 天 | 桌面签名、公证、升级回滚、发布演练 | I1、I2、I3 | 是 |
| I5 | 用户支持与可诊断性 | 5–8 天 | 本地日志、诊断包、FAQ、支持流程 | I2、I3 | 是 |
| I6 | Beta 验证与 Stable 决策 | 10–15 天 | 外部 Beta、指标复盘、商业路径、Go/No-Go | I0–I5 | 是 |

以单人开发计算，P50 约 46 个工程日，P80 约 60 个工程日。若某迭代发现数据损坏或安全高风险，应优先延长当前迭代，不压缩验证时间。

## 6. 全局优先级规则

| 优先级 | 定义 | 示例 | 处理规则 |
|---|---|---|---|
| P0 | 数据损坏、凭据泄露、远程代码执行、无法发布 | 恢复覆盖损坏、明文密码日志 | 立即停止其他工作 |
| P1 | 核心链路失败、升级失败、严重兼容问题 | 无法扫描、无法播放、签名失败 | 当前迭代必须完成 |
| P2 | 可绕过但明显影响信任或效率 | 错误文案、诊断不足 | 排入本计划对应迭代 |
| P3 | 体验增强或新能力 | 新格式、新主题、新 AI 模式 | 商业成熟化完成前冻结 |

## 7. 统一 Definition of Ready

事项进入迭代前必须满足：

- [ ] 问题与用户/业务风险描述清楚；
- [ ] 有可复现步骤或当前证据；
- [ ] 范围内与范围外已明确；
- [ ] 验收标准可自动或人工验证；
- [ ] 依赖与风险已登记；
- [ ] 单个故事不超过 8 点，超过则拆分；
- [ ] 不以“完成编码”作为唯一完成标准。

## 8. 统一 Definition of Done

所有迭代事项至少满足：

- [ ] 代码或文档已完成评审；
- [ ] 新增/修改行为有对应测试；
- [ ] 前端构建、Rust 测试、格式与严格静态检查全部通过；
- [ ] 错误路径、回退路径和取消路径已验证；
- [ ] 用户可见行为同步更新文档；
- [ ] 不新增未声明联网行为；
- [ ] 不新增明文凭据和敏感日志；
- [ ] 产物、日志或截图等验收证据已归档；
- [ ] 没有未登记的 P0/P1 缺陷；
- [ ] 产品负责人完成验收。

## 9. 迭代运行方式

每个迭代采用以下节奏：

1. 启动：确认目标、容量、Committed 与 Stretch；
2. 每日：更新风险、阻塞与剩余工作，不在迭代中临时扩范围；
3. 中点检查：验证最危险的假设是否已经被测试；
4. 验收：逐项执行退出清单并保留证据；
5. 复盘：记录遗漏、返工原因和下一迭代调整；
6. 只有退出条件全部满足，才允许进入下一迭代。

建议跟踪指标：

- 承诺完成率 ≥ 85%；
- 中途范围变化 < 10%；
- 结转工作 < 15%；
- 所有 P0/P1 问题均有负责人和截止日期；
- 每个迭代至少形成一项可重复执行的自动验证。

## 10. Stable 总发布门禁

Stable 候选版本必须同时满足：

- [ ] 主分支 CI 连续 14 天无红灯；
- [ ] 核心链路自动化测试全部通过；
- [ ] 至少 3 类 WebDAV 服务端完成兼容验证；
- [ ] 至少 3 个历史数据库版本完成升级与回滚验证；
- [ ] Windows/macOS/Android 产物完成签名验证；
- [ ] 高危依赖漏洞为零，或已通过风险评审并限定修复日期；
- [ ] 隐私政策、联网清单、安全政策、支持文档已发布；
- [ ] 外部 Beta 用户达到退出指标；
- [ ] 完成一次正式发布演练和一次失败回滚演练；
- [ ] Go/No-Go 评审无未接受的发布阻断项。
