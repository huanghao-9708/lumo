# I0：产品契约与范围冻结

> 优先级：P0  
> 建议周期：3–5 个工程日  
> 建议容量：21 点 Committed，5 点 Stretch  
> 迭代目标：建立一个与真实产品一致、可被用户和团队共同信任的产品契约，并冻结商业成熟化期间的功能范围。

## 1. 背景

当前 VISION、README、移动端计划、AI PRD 和真实代码之间存在明显分叉，包括“是否联网”“是否做 AI”“WebDAV 是同步还是备份”“支持哪些平台和格式”等。文档不一致会直接造成错误营销、隐私承诺风险和无边界开发。

本迭代不改变功能，先统一事实、术语和决策机制。

## 2. 迭代成功标准

- 所有用户可见能力都有唯一状态：Stable、Beta、Experimental、Planned 或 Deprecated；
- 所有外部网络请求都有目的、触发条件、数据字段和关闭方式；
- “备份恢复”不再被描述为已具备合并能力的多设备同步；
- AI 是否属于核心产品方向形成正式决策；
- README、VISION、Release Notes 模板引用同一个事实源；
- 新功能冻结规则和例外审批机制生效。

## 3. 用户故事与估算

| ID | 用户故事 | 优先级 | 点数 |
|---|---|---:|---:|
| PC-001 | 作为用户，我希望产品承诺与实际行为一致，以便信任隐私和数据声明 | Critical | 5 |
| PC-002 | 作为新用户，我希望清楚知道功能稳定程度，以便决定是否导入重要曲库 | High | 3 |
| PC-003 | 作为维护者，我需要统一术语和事实源，以便所有文档与发布内容自动保持一致 | High | 5 |
| PC-004 | 作为产品负责人，我需要范围冻结与决策规则，以便成熟化工作不被新功能打断 | High | 3 |
| PC-005 | 作为发布负责人，我需要版本和发布通道政策，以便版本号代表真实稳定程度 | High | 5 |

## 4. 详细执行点

### PC-001：建立联网与隐私事实清单

- [ ] 搜索代码中的所有 HTTP/HTTPS 地址和动态 Base URL；
- [ ] 按 WebDAV、封面、歌词、AI、更新检查分类；
- [ ] 为每个请求记录触发入口、默认状态、发送字段、接收字段、缓存位置和超时；
- [ ] 标记请求是用户主动触发、用户授权后自动触发，还是应用默认触发；
- [ ] 验证关闭在线歌词/封面/AI 后不会产生对应请求；
- [ ] 记录第三方服务名称、域名、用途、失败降级和未来替换策略；
- [ ] 建立“新增外联必须同步更新清单”的评审规则；
- [ ] 输出 `resources/doc/product/NETWORK_BEHAVIOR.md` 草案。

验收标准：

```text
Given 全新安装且用户未开启任何在线增强能力
When 用户只导入并播放本地音乐
Then 除用户主动配置的 WebDAV 外，不产生未声明的外部请求

Given 用户开启在线歌词或封面
When 应用准备向第三方发送元数据
Then 设置页已明确说明服务商、发送字段和关闭方式
```

### PC-002：建立真实功能与平台矩阵

- [ ] 盘点 Windows、macOS、Linux、Android 的功能差异；
- [ ] 为扫描、播放、歌词、封面、WebDAV、备份恢复、AI、更新分别标状态；
- [ ] 列出已验证格式，不以底层库“理论支持”代替产品支持；
- [ ] 记录每项能力的验证环境与最后验证版本；
- [ ] 将无法证明的能力降级为 Beta 或 Experimental；
- [ ] 输出 `resources/doc/product/FEATURE_MATRIX.md`；
- [ ] README 只引用该矩阵，不再维护第二套状态列表。

验收标准：

```text
Given 任意 README 或发布说明中的功能声明
When 追溯其状态
Then 可以在 FEATURE_MATRIX 中找到对应平台、状态和验证版本
```

### PC-003：重写产品契约

- [ ] 明确核心目标用户：个人大曲库、NAS/WebDAV、隐私敏感用户；
- [ ] 明确核心问题：拥有音乐但发现、管理和跨设备访问体验差；
- [ ] 明确不可妥协原则：本地优先、默认离线、用户授权联网、数据可恢复；
- [ ] 决定 AI 是核心、可选增强还是实验能力；
- [ ] 明确“不做什么”，并删除已失真的“不做 AI”等条目；
- [ ] 定义 WebDAV 的三个独立能力：远程曲库、透明缓存、数据备份恢复；
- [ ] 将“同步”保留给未来真正具有冲突处理的实现；
- [ ] 输出不超过 4 页的 `resources/doc/product/PRODUCT_CHARTER.md`；
- [ ] 将旧 VISION 标注为历史文档或更新为引用 Product Charter。

### PC-004：功能冻结和变更控制

- [ ] 建立成熟化期间冻结清单；
- [ ] 定义允许插队的事项：安全、数据损坏、构建阻断、严重兼容；
- [ ] 新需求必须提供用户证据、商业价值、风险和延后代价；
- [ ] 建立 Decision Log 模板，记录关键取舍、日期、负责人和复审时间；
- [ ] 将未完成的新功能统一移入 `POST_STABLE_BACKLOG.md`；
- [ ] 每周审查一次范围变化，目标低于 10%。

### PC-005：版本和发布通道政策

- [ ] 定义 Nightly、Beta、Stable 的目的和受众；
- [ ] 定义 SemVer 使用规则及破坏性数据迁移规则；
- [ ] 限制 Stable 发版频率，禁止同日连续发布多个次版本；
- [ ] 定义热修复适用条件和最小验证集；
- [ ] 定义版本号单一来源和自动一致性检查；
- [ ] 定义支持窗口：当前 Stable、上一 Stable、Beta；
- [ ] 输出 `resources/doc/release/VERSION_POLICY.md`。

## 5. Stretch 项

- [ ] 形成一句话定位、三条核心价值和三条非目标；
- [ ] 准备官网/README 共用的用户向产品描述；
- [ ] 为 Experimental 功能设计统一标识文案。

## 6. 验证与评审

- [ ] 逐页交叉检查 README、VISION、AI PRD、移动端计划；
- [ ] 由开发者按真实代码复核联网清单；
- [ ] 找一位未参与开发的人阅读 Product Charter，确认不会误解“同步”和“隐私”；
- [ ] 用一次模拟发布验证 Release Notes 能从事实源生成；
- [ ] 记录所有仍有争议的产品决策和复审日期。

## 7. 风险与应对

| 风险 | 应对 |
|---|---|
| 为了保持旧承诺而隐瞒真实能力 | 以当前代码和用户行为为准，允许愿景正式演进 |
| 文档继续多头维护 | README、发布说明只引用事实源，不复制矩阵 |
| AI 定位争议拖延迭代 | 限时决策；无法决定时先标 Experimental |
| “同步”改名被认为是能力倒退 | 强调这是降低数据风险和纠正预期，不删除现有能力 |

- [ ] 功能与平台矩阵完整；

- [ ] 发布通道和版本政策确认；
- [ ] 新功能冻结规则开始执行；
- [ ] 文档没有互相矛盾的 P0 声明；
- [ ] I1 可以基于确定的 Stable 范围设计测试。
