## 5. 本轮决策记录

1. **门禁只拦"今天就能机器判定"的项**。不做假绿的山寨测试（例如给 Vue 组件写快照测试充当"前端覆盖"），缺口写进文档比刷绿更有价值。
2. **`release.yml` 内联复制门禁而不是跨工作流复用**。GitHub 不支持 `needs` 跨 workflow；用 `workflow_run` 串联会让发布依赖另一个 workflow 的完成状态，首跑调试成本高。代价是同一次 push 上 CI 与 preflight 重复计算，接受。
3. **Rust 工具链保持浮动 stable**，不写 `rust-toolchain.toml`。理由：本机 1.93.1 与 Android 交叉编译链耦合，钉死后 gen/android 构建环境需同步改；浮动代价是新 clippy lint 可能让 PR 变红——这属于可预期且必须在某次迭代处理的技术债，用 preflight 挡住发布即可。复审点：I4 签名与更新工程。
4. **`check-network-registry.mjs` 只校验"文件是否登记"，不校验 URL 是否穷尽**。图片实际主机由服务端响应决定（网易云 CDN、mzstatic），任何逐 URL 白名单都会假装可枚举并很快失真。
5. **前端测试框架选 `vitest@4 + @vue/test-utils@2 + happy-dom@20`，不选 Playwright/Jest/jsdom**（2026-09-18 产品负责人授权新增这三个 devDependencies）。理由：vitest 直接复用仓库已装的 vite 6（零新增构建链），happy-dom 比 jsdom 轻且足够覆盖"条件渲染 + 文案"这类断言；组件挂载用 `global.stubs.teleport` 打掉 `AppModal` 的 Teleport，不引入额外测试工具库。约束：三者**只进 `devDependencies`**，`vite build` 产物哈希与引入前逐字节一致，运行时包体不受影响；版本选择上刻意避开需要 Node ≥ 22 的 vitest 5，以匹配 CI 的 Node 20。复审点：引入 E2E（Playwright/WebdriverIO）时重新评估，那需要再一次授权。
   附带事实：`npm audit` 安装后剩 3 条 high（`brace-expansion`/`nanoid`/`postcss`），经与 `HEAD:package-lock.json` 比对**全部是既有传递依赖**，新增三包未引入任何新告警；未顺手 `npm audit fix`（会改动 vite/tailwind 的传递树，属 I1 之外范围），已登记为待办。
