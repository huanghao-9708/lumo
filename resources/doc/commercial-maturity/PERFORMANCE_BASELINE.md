# 性能基线（I3/DATA-005）

> 状态：v1，2026-09-18  
> 已测范围：**仅数据库/查询层**。  
> 未测范围：冷启动、热启动、首播、切歌、内存、安装包体积、本地磁盘 I/O、局域网/弱网 WebDAV——
> 这些项目在本文件给出实测区间之前，**任何对外声明一律禁止**（`FEATURE_MATRIX.md` §4 规则 7、
> `PRODUCT_CHARTER.md` §升级门槛）。

## 1. 可复现方式

```bash
# 唯一事实来源：基准代码本身，不在文档里手抄 SQL
cargo test --release --test perf_baseline -- --ignored --nocapture
```

- 代码：`src-tauri/tests/perf_baseline.rs`（默认 `#[ignore]`，不拖慢常规 `cargo test`）。
- 方法：每种规模预热 1 次，再计时 5 次，报告**中位数 / 最大值**（样本 5 个，P95 与最大值同义，
  故报 max；要 P95 需把 `RUNS` 提到 ≥20）。
- 被测对象是生产代码本身：`TrackRepo::get_tracks_paginated`、`init_db` 建出的真实 schema、
  与 `services/scanner.rs` 扫描前完全相同的缓存加载 SQL。复制一份 SQL 来测没有意义。
- 数据：生成式、匿名、不含任何用户内容；规模 1k / 10k / 30k 首。

## 2. 数据集定义

| 维度 | 取值 |
|---|---|
| 规模 | 1,000 / 10,000 / 30,000 首（每首 1 个 `media_files`，1 个 `track_artists`） |
| 专辑 / 艺人 | 每 8 首一张专辑；艺人数 ≈ 规模/6（`INSERT OR IGNORE` 去重） |
| 标题 | 中英混合（如「夜航船 Midnight Ferry」），长度不一——全 ASCII 会让 `LIKE` 扫描便宜得不真实 |
| 文件 | 统一 `.flac`，`file_size` ≈ 20MB（仅记录数值，不落真实音频文件），`duration_ms` = 210000 |
| 收藏 | 每 20 首 1 首进 `favorite_tracks` |
| 时间字段 | `added_at` 全部相同（迫使 `t.id` tiebreaker 生效，最坏排序情形） |
| 收尾 | `VACUUM` 后再量库体积 |

## 3. 实测结果

**测量环境（本机，一次性记录）**：Windows 10.0.26200 x86_64 · rustc 1.93.1 · `--release` ·
并行度 32 · 数据盘为系统盘（NVMe，未单独标定）。换机器必须重测并在下表另起一列，不得沿用。

| 指标 | 1,000 首 | 10,000 首 | 30,000 首 | 随规模增长 |
|---|---:|---:|---:|---|
| 建库导入（30k 含事务提交 + VACUUM 前） | 61 ms | 633 ms | 1,932 ms | ≈ 线性 |
| 首屏列表 200 条（中位 / 最大） | 4.2 / 4.6 ms | 40.3 / 40.9 ms | **127.6 / 131.4 ms** | **≈ 线性（O(N)）** |
| 深分页 `offset = N-200` | 3.9 / 4.8 ms | 41.8 / 43.6 ms | 141.7 / 143.4 ms | ≈ 线性 |
| 关键词搜索 `LIKE '%夜航%'` | 2.0 / 2.4 ms | 18.4 / 19.8 ms | 56.7 / 57.0 ms | ≈ 线性（全表扫，符合无 FTS 预期） |
| 扫描前全量缓存加载（`media_files` 全行） | 0.4 / 0.4 ms | 3.7 / 4.0 ms | 12.2 / 12.5 ms | ≈ 线性 |
| `PRAGMA integrity_check` | 5.1 / 5.4 ms | 53.8 / 55.0 ms | 171.6 / 172.7 ms | ≈ 线性 |
| 库体积（VACUUM 后） | < 0.05 MB | 5.41 MB | 15.84 MB | ≈ 0.53 KB/首 |

### 3.1 由本基线暴露的真实问题（登记，不在 I3 修）

- **首屏列表是 O(N)，不是 O(page)**。30k 首时取 200 条要 127.6 ms。
- 归因（同一基准内的对照指标）：**排序/分页本身不是瓶颈**——同排序条件下的裸 `SELECT t.id …
  ORDER BY added_at DESC, id LIMIT 200` 只要 6.4 ms；即约 **95% 的成本来自 SELECT 列表里的
  相关子查询**（艺人 `GROUP_CONCAT`、专辑名、时长、来源 kind）与 `media_files` join，
  它们在服务端对**全部 30k 行**求值后才被 `LIMIT` 截断。
- 处置：登记 `POST_STABLE_BACKLOG.md` B-20（>1 万首优化）。目标形态是先在内层
  `LIMIT` 出 200 个 id、再对这 200 行做装饰；预期把 30k 首的首屏拉回个位数毫秒。
  **优化后本文件必须重测并覆盖上表**，否则不得声明改进。
- 现有对外文案的影响：`FEATURE_MATRIX.md` §3 早已写明"不使用 20 万曲库不劣化"；
  本表进一步给出可引用区间——**查询层在 30k 首内可用，但列表首屏在 1 万首以上已可感知**。

  库体积单列阈值 10%。
