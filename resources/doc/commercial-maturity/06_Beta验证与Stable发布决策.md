# I6：Beta 验证与 Stable 发布决策

> 优先级：P0（Stable 前）  
> 建议周期：10–15 个工程日，至少覆盖 14 个自然日  
> 建议容量：21 点产品/工程工作 + 用户观察周期  
> 前置：I0–I5 全部通过退出条件  
> 迭代目标：用真实外部用户和可度量证据验证产品可靠性、价值主张与发布准备度，形成明确的 Go/No-Go 决策。

## 1. 成功标准

- 10–20 位非作者用户完成安装和核心任务；
- 至少覆盖 Windows、macOS、Android 和三类 WebDAV 环境；
- 连续两周没有未解决的数据损坏、安全或升级阻断问题；
- 用户能够理解本地优先、联网增强和备份恢复边界；
- 有足够证据判断核心价值主张是否成立；
- 商业/开源路径、品牌和支持边界形成阶段性决策；
- Stable 发布由门禁决定，不由日期或功能数量决定。

## 2. 用户故事与估算

| ID | 用户故事 | 优先级 | 点数 |
|---|---|---:|---:|
| BETA-001 | 作为潜在用户，我希望安全加入 Beta 并知道风险，以便决定是否导入真实曲库 | Critical | 3 |
| BETA-002 | 作为产品负责人，我需要观察首次价值达成，以便判断定位是否成立 | Critical | 5 |
| BETA-003 | 作为维护者，我需要结构化缺陷与兼容反馈，以便完成 Stable 收敛 | Critical | 5 |
| BETA-004 | 作为项目所有者，我需要明确商业与开源路径，以便后续投入可持续 | High | 5 |
| BETA-005 | 作为发布负责人，我需要客观 Go/No-Go 清单，以便不带风险进入 Stable | Critical | 3 |

## 3. Beta 样本设计

### 3.1 建议用户构成

- 4–6 位仅使用本地音乐的桌面用户；
- 4–6 位 NAS/WebDAV 用户；
- 2–4 位 Android 后台播放用户；
- 2–4 位大曲库用户（10,000 首以上）；
- 至少 3 位不熟悉项目、无法接受开发者现场指导的新用户；
- AI 电台作为可选分组，不让它干扰基础播放器验证。

同一用户可以属于多个分组，但应记录平台、曲库规模、来源类型和使用频率。

### 3.2 排除条件

- 只由作者本人验证；
- 只运行一次启动冒烟；
- 全部用户使用同一操作系统或同一 WebDAV 服务；
- 在测试期间由开发者手动修改用户数据库；
- 未告知 Beta 风险就导入唯一数据副本。

## 4. 详细执行点

### BETA-001：Beta 招募与安全进入

- [ ] 准备 Beta 说明：目标、周期、风险、支持范围和退出方式；
- [ ] 明确要求保留原音乐和数据库备份；
- [ ] 提供签名安装包及校验方式；
- [ ] 记录用户同意提供的反馈类型，不默认收集遥测；
- [ ] 为每位用户分配匿名 Beta ID；
- [ ] 收集平台、曲库规模、来源类型和目标场景；
- [ ] 提供安装、首次导入和诊断导出指南；
- [ ] 建立每日可查看的 Known Issues；
- [ ] 允许用户随时退出并说明数据清理方式。

### BETA-002：首次价值与留存验证

- [ ] 定义首次价值：成功导入/连接曲库并连续播放三首歌曲；
- [ ] 记录安装完成率；
- [ ] 记录首次导入成功率和所需时间；
- [ ] 记录首次播放成功率；
- [ ] 记录 WebDAV 配置成功率；
- [ ] 第 1、3、7、14 天进行简短回访；
- [ ] 询问用户最常使用的三项能力；
- [ ] 询问卸载或停止使用原因；
- [ ] 验证用户是否理解在线歌词/封面/AI 会发送什么；
- [ ] 验证用户是否把备份恢复误解为实时同步；
- [ ] 收集“如果 Lumo 消失，最舍不得什么”的回答；
- [ ] 不用作者的个人偏好替代用户证据。

建议指标：

| 指标 | Stable 建议门槛 |
|---|---:|
| 安装成功率 | ≥ 90% |
| 首次本地导入成功率 | ≥ 90% |
| WebDAV 首次配置成功率 | ≥ 80% |
| 首次播放成功率 | ≥ 95% |
| 7 日仍在使用 | ≥ 60% |
| 14 日仍在使用 | ≥ 50% |
| 用户可正确解释联网边界 | ≥ 80% |
| 用户误解备份为合并同步 | ≤ 10% |

样本较小时指标只作决策参考，不伪装成统计显著结论。

### BETA-003：缺陷收敛与兼容验证

- [ ] 所有反馈进入统一看板并按 S0–S3 分级；
- [ ] S0/S1 在当天完成确认和风险隔离；
- [ ] 每个缺陷记录版本、平台、复现率和诊断证据；
- [ ] 对无法复现问题安排一次远程复核或增加诊断；
- [ ] 修复必须附回归测试；
- [ ] Beta 期间只接受阻断缺陷修复，不插入新功能；
- [ ] 每次 Beta 更新附变化、风险和回滚步骤；
- [ ] 跟踪崩溃自由会话、播放失败、扫描失败、恢复失败；
- [ ] 验证三类 WebDAV 服务和不同网络条件；
- [ ] Beta 结束前连续 7 天无新增 S0/S1；
- [ ] 对遗留 S2/S3 明确是否进入 Known Issues。

### BETA-004：商业与开源路径决策

- [ ] 确认未来 12 个月主要目标：作品影响力、用户规模、收入或技术验证；
- [ ] 分析 MIT 继续开放的收益和代码可复制风险；
- [ ] 评估品牌/商标是否作为主要护城河；
- [ ] 评估开源免费、赞助、商店买断、付费移动端、付费支持等路径；
- [ ] 访谈用户的支付意愿和最愿意支付的价值，不直接问“你会不会付费”；
- [ ] 估算代码签名、域名、商店、支持时间和基础设施成本；
- [ ] 明确哪些承诺个人项目无法长期承担；
- [ ] 决定是否建立官网、域名和公开路线图；
- [ ] 对未来版本许可证变化进行法律可行性评估；
- [ ] 输出一页 `BUSINESS_DECISION.md`，包含选择、未选方案和复审日期。

### BETA-005：Stable Go/No-Go 评审

- [ ] 汇总 I0–I5 退出证据；
- [ ] 汇总 Beta 指标、缺陷、用户反馈和兼容结果；
- [ ] 检查所有 S0/S1 是否关闭；
- [ ] 检查安全例外是否仍在有效期；
- [ ] 检查签名证书、更新元数据和回滚通道；
- [ ] 从干净环境执行最终安装与升级冒烟；
- [ ] 使用历史数据库执行最终迁移；
- [ ] 抽查隐私抓包与诊断包脱敏；
- [ ] 确认 Release Notes、Known Issues、支持入口和恢复指南；
- [ ] 记录 Go、Conditional Go 或 No-Go 决策；
- [ ] Conditional Go 必须写明条件、负责人和截止时间；
- [ ] No-Go 不通过降低标准解决，而是回到对应迭代。

## 5. Stable 决策评分卡

| 维度 | 权重 | Go 门槛 |
|---|---:|---:|
| 数据可靠性 | 25% | 无开放 S0，恢复/迁移全过 |
| 核心可用性 | 20% | 首次播放 ≥95%，无开放 S1 |
| 安全与隐私 | 20% | 签名、CSP、凭据、隐私门禁全过 |
| 跨平台发布 | 15% | 支持平台安装/升级矩阵通过 |
| 用户理解与价值 | 10% | 核心定位得到多数用户确认 |
| 支持准备度 | 10% | 诊断、文档、响应流程可用 |

总分建议达到 85/100，且数据可靠性、安全隐私两个维度不得用其他分数补偿。

## 6. 发布后 30 天观察

- [ ] 每周检查新增 S0/S1、安装失败和升级失败；
- [ ] 统计重复支持问题并补 FAQ；
- [ ] 复盘第三方元数据服务稳定性；
- [ ] 记录 Stable 到热修复的原因和时间；
- [ ] 不因发布完成立即恢复功能堆叠；
- [ ] 30 天后再决定下一阶段路线图。

## 7. 风险与应对

| 风险 | 应对 |
|---|---|
| Beta 用户过于熟悉项目 | 至少 3 位完全新用户，不提供现场指导 |
| 零遥测导致指标不足 | 使用自愿回访、本地诊断和结构化测试任务 |
| 小样本指标波动大 | 结合访谈和缺陷证据，不做虚假统计推断 |
| 用户反馈推动功能扩张 | 记录到 Post-Stable Backlog，不中断收敛 |
| 为赶日期放宽门禁 | Stable 由证据决定，无固定发布日期承诺 |

## 8. 退出清单

- [ ] 至少 10 位外部用户完成两周 Beta；
- [ ] 平台、曲库规模和 WebDAV 类型具有基本代表性；
- [ ] 连续 7 天无新增 S0/S1；
- [ ] Stable 总发布门禁全部有证据；
- [ ] 用户能够理解联网、隐私和备份恢复边界；
- [ ] 商业/开源路径形成阶段性决策；
- [ ] Go/No-Go 会议形成书面记录；
- [ ] 发布后 30 天观察计划已指定负责人。
