## 1. 目标与决策原则

用户观察到 Lumo 播放时约 700 MB，希望回到“轻量级音乐播放器”的定位。这个数字尚未记录版本、曲库规模、进程范围和 Windows 内存指标，不能直接等同于 JavaScript 堆、WebView2 或播放器解码器的占用，也不能与另一款播放器的任务管理器数字直接比较。

本轮先完成**测量 → 定位 → 分项改造 → 对照验收**。保留现有 Rust 播放、曲库和扫描核心。只有在完成高收益治理后，Windows 整组进程仍无法接近目标，才启动原生界面样机。换框架本身不算内存治理成果，必须由同场景数据证明。

| 层级 | 目标 | 判定 |
|---|---|---|
| 事实基线 | 复现约 700 MB 的场景，按进程和内存类型拆解 | 保存原始采样、环境、复现步骤；未复现则记录差异，不倒推原因 |
| 当前架构治理 | 在同机、同曲库、同场景下，30 分钟播放的稳态整组私有工作集降至**基线的 50% 以下** | 这是阶段目标，不预先承诺具体 MB；各阶段都要看内存与交互延迟 |
| 长期产品目标 | 探索 Windows 播放稳态整组私有工作集 **≤100 MiB** | 若现有 WebView2 架构达不到，原生样机与其同口径对比后再决策；不得把 PoC 数字写成产品承诺 |
| 防回弹 | 相同场景 60 分钟后，稳态值较第 10 分钟增加不超过 20 MiB 且不超过 10% | 排除预期缓存填充后再判断；超出时保留快照定位 |

“稳态”定义为场景开始后经过 2 分钟预热、无扫描和下载任务时的采样中位数；峰值另报，不以单次任务管理器截图代替时序数据。达不到阶段目标时仍须提交真实结果和原因，不得通过隐藏窗口、强制 GC 或降低音质制造数字。

## 2. 统一测量口径

### 2.1 进程与指标

Windows 上把 Lumo 主进程及其对应的 WebView2 浏览器、渲染器、GPU、网络/音频等辅助进程视为一个产品进程组。通过进程树、命令行中的用户数据目录和 WebView2 Browser Task Manager 交叉核对归属；不能把其他应用的 `msedgewebview2.exe` 算进来。WebView2 有多个进程是正常架构，参见[微软进程模型](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/process-model)。

| 指标 | 用途 | 注意 |
|---|---|---|
| 每进程及整组 **Private Working Set** | 主验收指标：当前实际驻留的私有物理页 | 不把共享页重复相加；同时保留每进程明细 |
| 每进程及整组 **Private Bytes / Commit Size** | 辅指标：进程已提交的私有虚拟内存 | 工作集下降但提交持续增长时，继续查缓存或泄漏 |
| WebView2 Browser Task Manager 的 JS heap、原生内存 | 区分 JS 对象、DOM/图片与浏览器引擎 | DevTools 本身会影响测量；主基线关 DevTools，诊断轮单独开 |
| GPU 专用/共享内存、句柄数、线程数、CPU | 发现把 RAM 压力转成显存或异常资源增长 | 作为解释指标，不混进“100 MiB”主指标 |
| 磁盘音频缓存容量 | 防止把磁盘缓存误判为内存 | 当前音频缓存上限 2 GiB 是磁盘配额，不是 RAM 占用 |

先制作 `scripts/measure-memory.ps1`：启动前登记构建 SHA、Windows/WebView2 版本、内存容量、缩放、显示器、曲库规模；每 2 秒记录时间戳、场景标签、PID、进程类别、Private Working Set、Private Bytes、Working Set、CPU、句柄与线程数到 CSV；输出整组中位数、P95、峰值及各进程贡献。进程归属要在采样脚本里固定并人工抽查一次，不能只按进程名求和。

每个场景至少做 3 次独立启动，报告中位数与最大值。主基线使用 **release 安装包、关闭 DevTools、固定 1200×720 窗口**；诊断轮可用 Edge DevTools Heap Snapshot、Detached Elements 和 WPR/WPA，但不把诊断轮数据与主基线混算。[微软 WebView2 性能指南](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance)和[Windows 内存分析指南](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/memory-footprint-optimization)是工具依据。

### 2.2 固定场景

| ID | 场景 | 观察点 |
|---|---|---|
| S0 | 新配置、空曲库冷启动与热启动，各静置 5 分钟 | 框架本底、启动后的缓存填充 |
| S1 | 1k / 10k / 30k 首曲库进入首页、全部歌曲、专辑、艺人；各静置 2 分钟 | 数据量斜率、封面与列表占用 |
| S2 | 30k 曲库持续滚动歌曲列表和专辑网格 10 分钟，再静置 5 分钟 | 图片缓存增长、虚拟列表回收、IPC 排队 |
| S3 | 本地 MP3 / FLAC 各播放 30 分钟；切歌、暂停、Seek、打开沉浸页 | 解码缓冲、歌词/封面、长期稳态 |
| S4 | 反复切换 20 次歌曲/专辑/艺人/详情/搜索，再静置 5 分钟 | 监听器、定时器、DOM 与对象保留 |
| S5 | 30k 曲库本地扫描、旧库补扫；另测 WebDAV 扫描和远程播放 | 扫描临时表、连接缓存、网络缓冲峰值 |
| S6 | 最小化或后台静置 30 分钟后恢复 | 后台占用与恢复时延 |

S0–S4 首先用匿名可复现曲库跑通，再用经授权的真实曲库复核。真实库的封面尺寸分布、专辑数与歌曲格式需记录；基准报告不包含文件名、凭据、封面或音频内容。WebDAV 场景固定网络条件并单列，不能与本地播放混用。

Android 使用 S0、S1、S3、S4 的等价移动场景，额外测锁屏后台播放、前后台切换和系统回收后恢复。记录 PSS、USS、RSS 及 Java/Native/Graphics 分项，使用[Android 官方 `dumpsys meminfo` 指南](https://developer.android.com/topic/performance/memory/guide/tools-overview)和 Android Studio Profiler；不得把 Android PSS 与 Windows 私有工作集放在同一张绝对值排行榜里。macOS/Linux 先确认共享图片与列表改动不退化，再各自建立平台原生指标基线；Windows 的 100 MiB 目标不直接套用到其他操作系统。

## 3. 代码现状与待验证假设

以下只是**优先调查对象**，不把代码上限当成已发生的 700 MB 根因。

| 优先级 | 证据位置 | 风险假设 | 验证动作 |
|---|---|---|---|
| P0 | `src/utils/artworkCache.ts`：`MAX_ENTRIES = 5000`，原图 Blob 转 data URL；注释按 50 KB/张估约 330 MB | 只有“张数”上限，没有字节上限；原图尺寸和解码副本会放大占用 | 记录缓存条数、编码后总字节、最大单图、页面切换前后差值；禁用该层做受控对照 |
| P0 | `src-tauri/src/db.rs`：连接池 24、每连接 `cache_size = 8000` 页；扫描连接另设 64 MiB | 若 24 条连接各自填满 4 KiB × 8000 页，理论页缓存上限约 750 MiB；**不是实际占用** | 测活跃/空闲连接数、页大小与缓存使用量；分档压缩后测并发 IPC 与扫描吞吐 |
| P0 | `album_repo.rs` 等把 SQLite 缩略图编码为 Base64 放进 DTO；`player.ts` 长期保存 `cover_thumb` | 图片字节跨 SQLite、Rust、IPC、JS 与浏览器解码层复制 | 对 1k/10k/30k 专辑记录 DTO 体积、JS heap、图片请求与滚动时延 |
| P1 | `player.ts` 的 `tracks.value.push(...newTracks)`；收藏、歌单等入口整批取回；`useVirtualList.ts` 只虚拟 DOM | DOM 虚拟化不代表数据数组有界，长时间翻页仍可能增长 | 记录每个视图加载条数、队列条数和离开视图后的保留对象 |
| P1 | `scanner.rs` 的来源文件 `HashMap` 与 64 MiB SQLite 临时页缓存 | 30k+ 扫描峰值可能叠加多份索引与图片处理缓冲 | 在 S5 抓主进程峰值、分阶段分配和扫描耗时 |
| P2 | `useArtworkSrc.ts` 的预取队列、`useCoverColor.ts` 的图片/canvas、全局事件监听 | 快速切换和异步任务可能使已离开页面的对象继续存活 | S4 前后 Heap Snapshot 差分、Detached Elements、待处理请求数 |

仓库现有[性能基线](commercial-maturity/PERFORMANCE_BASELINE.md)只测 1k/10k/30k 数据库查询，并把应用内存明确列为未测。既有[分页 IPC 调查](专辑艺人分页IPC队列延迟调查_2026-09-20.md)记录了 WebView2 在滚动动画期间延迟请求，也证明“关闭图片就能解决卡顿”的假设不成立。因此更换图片通道时必须同时比较内存、封面可见时间与 IPC 排队，不能只看 RAM。

## 4. 分阶段实施

### 阶段 A：建立可复现基线（先于优化）

1. 固定 v2.0.0 release 包、测试机与匿名曲库；执行 S0–S6，保存 CSV、环境和复现步骤。
2. 在诊断构建增加**仅开发模式启用**的轻量计数：封面内存缓存字节/条数、前端列表条数、活跃 DB 连接、扫描文件缓存条数、正在进行的图片请求。计数不得记录用户内容。
3. 对最高的两个场景分别拍 WebView2 JS 堆快照和 Windows WPR 内存轨迹，得到“主进程 / renderer / GPU / SQLite / 图片”的贡献排序。
4. 将结果写入 `resources/doc/commercial-maturity/PERFORMANCE_BASELINE.md` 新的“应用内存”章节；保留原始数据在不含隐私的基准目录，不把单次截图当结论。

**退出条件：**700 MB 可复现或差异已解释；每个优先项有实测贡献、预期收益与回归风险。未过此门不宣布“已解决内存问题”。

### 阶段 B：封面与图片链路（最高优先）

1. 把 `artworkCache.ts` 的“5000 张”改为**按编码后字节数计量的 LRU**。先以 16/32 MiB 两档 A/B，保留命中率与驱逐计数；单图超限不进入缓存。页面离开后不保留原始封面 data URL。
2. 列表和网格只解码接近展示尺寸的图（例如 64/200 px），沉浸页单独请求较大版本；保留后端现有缩略图生成逻辑，避免用原始大图缩成小 `<img>`。
3. 对内联 Base64 方案与稳定缩略图 URL 方案做同场景 A/B。URL 方案以 `artwork_id + size` 为键，设置可验证的 HTTP 缓存头、请求合并、并发上限、可视区懒加载；只有在内存下降且 S2 滚动/IPC 不退化时替换内联方案。过渡期不要同时保留 Base64 和 data URL 两份长期缓存。
4. 封面清理与替换时检查 `Blob`/object URL、图片解码、颜色提取异步任务的取消和释放；颜色提取只对当前播放封面进行。

**回退条件：**封面可见时间或 S2 滚动/分页延迟较基线恶化超过 20%，或占位/闪烁明显增加。先回退图片通道，再保留已验证有效的字节上限。

### 阶段 C：数据库、扫描与播放缓冲

1. 将 24 条连接与每连接 8000 页作为实验参数，不直接拍脑袋改成固定值。先比较连接池 4/8/12 与 `cache_size = -2048/-4096/-8192`（SQLite 负值按 KiB 解释）组合；记录连接等待、IPC P95/P99、扫描吞吐和内存。选择满足并发链路的最小组合。
2. 对 `scanner.rs` 的 64 MiB 页缓存比较 8/16/32 MiB；来源文件索引按批次或紧凑结构处理，避免同一批文件的路径与元数据在多个容器里长期重复。补扫必须保持逐来源正确性。
3. 检查图片处理和 WebDAV/本地播放读入方式，禁止把整张超大原图或整首音频长期复制到内存。现有音频缓存 2 GiB 属磁盘策略，单独评估磁盘占用，不把它作为降低 RAM 的主要动作。
4. 数据库变更必须复跑 1k/10k/30k 查询基准、真实曲库分页与并发封面请求；内存收益与响应时延并列报告。

**回退条件：**数据库操作 P95 较基线恶化超过 20%，新增 `SQLITE_BUSY`/连接超时，或播放中出现可感知断音。

### 阶段 D：有界前端状态与生命周期

1. 所有歌曲视图统一分页契约。可视窗口保留有限数据页（首轮试 200/500 条两档），列表总数、选择状态、播放队列使用 ID/轻量摘要；离开视图释放整批 DTO。播放队列、全选和搜索必须验证语义不变。
2. 大列表检查 `ref` 深层响应式开销；对无需逐项深响应的 DTO 评估 `shallowRef` 与不可变更新。避免在内存里同时保留 DTO、映射对象、搜索副本和队列完整副本。
3. 对快速切页、封面变更、沉浸页开关做 Heap Snapshot 差分；清理事件监听、观察器、定时器和异步请求。重复 20 次后对象数量应回到稳定区间。
4. Android 与桌面共享的 `player.ts`/DTO 路径必须分别回归，不能为了 Windows 内存牺牲移动端播放和导航。

**回退条件：**长歌单播放、批量操作、滚动位置恢复或搜索结果不一致；数据窗口策略需要在功能回归通过后才启用。

### 阶段 E：原生界面决策（条件触发）

若 A–D 完成后，实测瓶颈仍主要是 WebView2 固定开销，且 ≤100 MiB 为必须达到的产品指标，做两个**只含首页、30k 歌曲列表、封面、播放栏与播放控制**的样机，不先全量重写：

- **Rust + Slint**：直接复用 Rust 核心；在 Windows 中文字体、输入法、图片与 30k 列表上测试实际渲染器和内存。Slint 的轻量软件渲染器目前对文字有能力限制，不能据此推断中文版样机的结果，参见[渲染器说明](https://docs.slint.dev/latest/docs/slint/guide/backends-and-renderers/backends_and_renderers/)。
- **Qt Widgets + Rust 核心桥接**：用 `QAbstractItemModel`/`QTableView` 测桌面大列表；另评估跨语言维护、打包和 Android 界面分离成本，参见[Qt Model/View 文档](https://doc.qt.io/qt-6/modelview.html)。

同机、同曲库、同窗口、同封面与播放操作，比较整组 Private Working Set、Private Bytes、CPU、首屏、滚动和 30 分钟增长。只有某样机同时达到目标、交互质量合格且迁移成本可接受，才写正式迁移计划。不要用 Electron 或 Qt WebEngine 作为“去浏览器内存”的替代方案。

| 性能回归 | 现有 `cargo test --release --test perf_baseline -- --ignored --nocapture` 继续通过并更新结果；S2 分页/滚动、首播和切歌时延不明显退化 |

单元测试覆盖 LRU 字节计数与驱逐、分页窗口边界、连接池配置和取消后的状态清理。Windows 内存时序基准在固定测试机或专门的夜间工装运行；共享 CI runner 资源波动大，只做功能/构建门禁，不用它的单次 MB 数阻断 PR。所有优化以**内存、CPU、交互时延、磁盘 I/O、功能正确性**共同验收。

## 6. 执行顺序

1. **先做 A**：建立基线和归因，不动产品行为。
2. **再做 B**：先压缩最明显的图片内存上限，逐步比较传输方案。
3. **并行评估 C 的参数矩阵，随后落地**：用实测连接等待和扫描吞吐选值。
4. **做 D**：统一各列表的数据生命周期，防止用户长时间使用后重新涨回去。
5. **复测完整 S0–S6**，记录未达标项；仅在条件成立时启动 E 的原生界面样机。

每阶段结束都更新本文件的“状态/实测链接”和 `PERFORMANCE_BASELINE.md`。本方案不预先声称 WebView2、SQLite 或封面中的任何一项就是 700 MB 的唯一根因。
