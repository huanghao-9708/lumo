# PRD：AI 推荐歌单（AI 电台）

> **日期**：2026-09-12
> **状态**：v1 已实现（随 v1.8.0 发布）；v1.1/v2 待排期
> **关联**：[首页与性能优化迭代记录](首页与性能优化迭代记录_2026-09-11.md)（智能歌单、首页排行榜为其上位功能）

---

## 1. 摘要（Summary）

在 LUMO 中新增「AI 推荐歌单」：基于**最近播放**、**某首种子歌**或**一句话描述**，从用户本地曲库中生成 20-30 首的真实歌单。AI 只负责"理解和选择"，候选与结果全部来自本地数据库（两段式架构，杜绝幻觉歌曲）。模型接入走用户自备的 OpenAI 兼容接口（云 API 或本地 Ollama 二选一），默认关闭、钥匙串存密、歌词与音频永不出本机。

|---|---|---|

## 3. 背景（Background）

- **现状**：曲库规模 32,466 首 / 3,838 专辑 / 1,893 艺人，但发现手段只有四条死规则智能歌单（播放最多/最近添加/最近播放/未曾播放）和首页 Top5 排行榜。"32k 首里今天想听什么"没有答案。
- **为什么是现在**：七轮性能迭代后 IPC 链路干净（启动 2 个请求、榜单 6ms），首页有了承载入口；`playlists` 表预留了 `kind='smart'` + `smart_rules_json`；P1-08 的钥匙串基础设施可复用于 API key。
- **刚变得可行的能力**：OpenAI 兼容接口成为事实标准——同一套调用代码同时覆盖云端 API 与**本地 Ollama**（`http://localhost:11434/v1`），后者让"本地曲库 + 本地模型"形成完全离线闭环，与本项目 local-first 的气质完全一致。

### 真实库元数据丰度（2026-09-12 只读实测，直接决定设计）

| 信号 | 实测 | 结论 |
|---|---|---|
| genres / track_genres | **0 行** | 流派过滤不可用，一句话模式靠 AI 从标题/艺人文本语义筛选 |
| albums.release_year | **0/3838** | 年代过滤不可用 |
| lyrics 覆盖 | **29,560/32,466（91%）** | 本地最丰富的语义信号；按隐私约定不出本机，v2 本地 embedding 的核心依据 |
| skip_count | **从未维护（全 0）** | 负向信号缺失；补录逻辑列入 v1.1 |
| play_count>0 | 126 首；近 30 天 play_history 117 条 | 冷启动严重：候选池必须有"历史不足"兜底 |
| 曲名语言 | 中文 ~24k、日文 ~1.5k | 语言类请求可用文本特征 + AI 筛选满足 |

## 4. 目标（Objective）

- **业务收益**：把"本地曲库的所有权优势"变成差异化能力——云端流媒体不可能为用户自己的本地文件做推荐。
- **用户收益**：不整理、不手动建歌单，说一句话或点一下就得到一份可信（全部真实存在）的歌单。

**Objective**：让用户每周都愿意打开一次 AI 电台，而不是只听固定几张专辑。

- **KR1**：幻觉率 = 0（生成的每一首都能回表命中，校验层强制保证）。
- **KR2**：三种模式在真实曲库上人工评分，"命中当下心情"的比例 ≥ 60%（每次生成 20 首中 ≥ 12 首可接受）。
- **KR3**：生成一次的等待中位时长 ≤ 15s（本地 Ollama 14B 级模型口径），且全程可取消。

## 5. 目标人群（Market Segment）

- **"仓库型"听众**：拥有上万首本地文件的人，需要"帮我从自己的仓库里翻出今天想听的"，因为曲库大到连自己都不知道有什么。
- **情境化收听者**：需要"下雨天/深夜写代码/跑步"配乐的人，因为情绪场景无法用播放次数这类统计规则表达。
- **隐私敏感者**：因为听歌历史过于私人，拒绝把整个曲库元数据同步给任何云服务的人。

## 6. 价值主张（Value Proposition）

| | 云端流媒体每日推荐 | 现有规则智能歌单 | LUMO AI 电台 |
|---|---|---|---|
| 只推本地真实存在的歌 | ✗（推自家版权库） | ✓ | ✓（校验层强制） |
| 理解自然语言/情绪 | ✓ | ✗ | ✓ |
| 数据不出本机 | ✗ | ✓ | ✓（Ollama 全离线可达） |
| 对象是"我的"曲库 | ✗ | ✓ | ✓ |

- **解决的问题**：本地曲库大而无当 → 变成可对话的曲库。
- **刻意不投入**：不做云端曲库推荐、不做社交、不做训练/个性化模型微调（用户显式反馈循环归入 v2）。

## 7. 方案（Solution）

### 7.1 UX / 流程

**入口**：首页「快速访问」区顶部新增一张横幅卡「AI 电台 — 基于你的曲库生成歌单」（数据来自曲库本身，横幅常驻；未开启 AI 时点击跳设置页对应分区）。

**生成页 `AiPlaylistView`**（替换 MainContent 当前视图，同专辑详情同级）：

```
┌──────────────────────────────────────────────┐
│  AI 电台            [基于最近播放|这首歌|一句话]  │
│  ──────────────────────────────────────────  │
│  [最近播放] 一键生成按钮（无输入）              │
│  [这首歌]   种子歌搜索框（选一首库内歌曲）      │
│  [一句话]   文本框："下雨天写代码的纯音乐"  [生成] │
│                                              │
│  ── 生成结果：{AI 起的歌名}                    │
│  {AI 写的一句话简介}               [重新生成]   │
│  01 歌名 — 艺人        因为…（一句话理由）      │
│  02 …                                        │
│  [▶ 播放全部]  [保存为歌单]                    │
└──────────────────────────────────────────────┘
```

- 生成中：骨架行 + 取消按钮；失败显示可读原因 + 重试；降级到规则歌单时顶部标注「AI 不可用，已按播放规则兜底」。
- P2：歌曲行 more 菜单「基于这首歌生成」（v1 从生成页的搜索框选种子）。

### 7.2 关键功能（P0/P1/P2）

1. **P0** 两段式生成：SQL 候选检索 → LLM 从候选中选择/排序/命名，输出 ID 必须属于候选（硬校验）。
2. **P0** 三种输入模式：最近播放 / 种子歌 / 一句话（共用一次 LLM 调用）。
3. **P0** BYOK 设置分区：开关（默认关）、Base URL、Model、API Key（钥匙串）、测试连接。
4. **P0** 降级链：校验失败重试一次 → 规则歌单兜底（复用现有智能歌单查询）。
5. **P1** 每首歌一行推荐理由（同一次调用输出，JSON 多带一个字段）。
6. **P1** 保存为歌单：落 `playlists`（`kind='manual'`），`smart_rules_json` 写入 `{origin:'ai', mode, prompt, seed_track_id, model, generated_at}` 供「重新生成」。
7. **P2** 歌曲行右键「基于这首歌生成」；「更安静一点」式反馈重生成（把上一轮结果与反馈追加进 prompt）。
8. **P2** 跳过信号补录（切歌时 `skip_count + 1`），进入候选权重。

### 7.3 技术设计

**架构：两段式，AI 永不直接面对全库**

```
前端 AiPlaylistView
   │  ai_generate_playlist(mode, phrase?, seed_track_id?, exclude_ids?)   ← 单个命令
   ▼
services/ai.rs
   ├─ ① 候选检索（纯 SQL，毫秒级，目标 200-500 首）
   │     recent 模式：最近 100 条 play_history 涉及曲目 + favorite_tracks
   │                  + play_count Top200；不足 300 时按 added_at 分层随机补齐
   │     seed 模式：同艺人全曲 + 同专辑 + 标题/艺人 LIKE(种子关键词) + 随机池 200
   │     phrase 模式：AI 预解析出的关键词 LIKE(标题/艺人) 命中 + 大池随机抽样 500
   │     * 流派/年代字段为空，不参与 v1 检索（见背景实测）
   ├─ ② prompt 组装：系统提示（规则+输出 JSON schema）+ 候选紧凑列表
   │     （id|标题|艺人，每行一条；500 行 ≈ 15-20k tokens）
   ├─ ③ 调用：reqwest POST {base_url}/chat/completions，
   │     response_format=json_object，temperature=0.8，超时 60s，AbortHandle 可取消
   ├─ ④ 校验：解析 JSON → track_ids ∩ 候选集（保序）→ 不足 15 首重试一次
   │     （重试时把"上一轮非法 ID"点名告知）→ 仍不足则规则兜底
   └─ ⑤ 回表：TrackRepo 按候选 13 列模板回查完整 TrackDTO + 附加理由
```

- **命令**（新 `commands/ai.rs`，均 `#[tauri::command(async)]`）：
  - `ai_generate_playlist(mode, phrase?, seed_track_id?) -> AiPlaylistResult`
  - `ai_get_settings() / ai_save_settings(...)`（key 经 `secret.rs` 入钥匙串，DB 只存 `##kr:` 引用——与来源密码同机制）
  - `ai_test_connection() -> { ok, model, latency_ms }`
- **设置存储**：新迁移建表 `ai_settings(id=1, enabled, base_url, model, temperature, credential_ref, updated_at)`。
- **模型**：`AiPlaylistResult { name, description, source: 'ai'|'fallback', tracks: Vec<AiRankedTrackDTO>, degraded_reason? }`；`AiRankedTrackDTO = TrackDTO flatten + reason: Option<String>`。
- **前端**：`api/ai.ts` + `stores/ai.ts`（设置与最近一次结果）+ `AiPlaylistView.vue` + `BatchActionBar` 不可用（结果页无多选，v1 保持简单）；首页横幅卡。
- **隐私红线**：prompt 只含 id/标题/艺人（v1）；歌词内容、音频、路径永不进入请求；`enabled=false` 时命令直接返回未开启错误，不发任何网络请求。Ollama 用户（`localhost` base URL）天然零外发。

### 7.4 假设与验证计划

| 假设 | 验证方式 |
|---|---|
| 500 首候选的紧凑列表能被 14B 级模型稳定按 JSON 返回 | 真实库上三模式 × 各 10 次生成，统计解析成功率 |
| 只凭标题/艺人（无流派）的候选，AI 选择质量可接受 | KR2 人工评分；若 phrase 模式 <40%，v1.1 引入"标题关键词扩展检索" |
| Ollama 本地延迟可接受（≤15s 中位） | KR3 实测；不达标则把候选裁到 300 或提示用户换小模型 |

## 8. 发布（Release）

- **v1（MVP，体量 M）**：P0 全部 + P1 的理由与保存为歌单。设置页「AI 推荐」分区、AiPlaylistView、首页横幅。
- **v1.1（体量 S）**：跳过信号补录；种子歌右键入口；失败重试的提示词优化。
- **v2（体量 L，独立立项）**：**本地歌词语义检索**——91% 歌词覆盖是最大金矿，用 Ollama embedding 把歌词向量化存本地（不出本机），phrase 模式候选从"标题 LIKE"升级为"语义召回"；反馈式重生成。
- **v3（Later）**：口味画像（从 play_history 蒸馏的用户偏好摘要，作为常驻 system context）。
- **明确不做**：云端曲库推荐、账号体系、模型微调、自动后台生成。

**v1 成功标准**：KR1=0 且 KR3 达标，且作者本人在一周真实使用中保存了 ≥3 份 AI 歌单（行为验证）。
