## 〇、一段话版本

用户报"分页 IPC 排队 2s+"，第三方 AI 诊断为"图片阻塞"。调查经历了**三轮误判**（图片论 → DevTools 放大器论 → wry 管道排队论），最终靠"三视角时间戳对齐 + requestId 时钟源取证 + 同实例控制变量实验"定位真因：**Chromium 资源调度器在滚动动画期间扣留渲染器新发起的网络请求**。一行 `--disable-smooth-scrolling` 使同场景从 7985ms 降到 116ms，当日结案合入 main。

## 二、完整时间线

### 阶段 A：第一轮冲锋——顺着"图片论"做实验（11:45 – 13:00，分支 `exp-disable-cover-render`）

这一阶段的隐含假设始终是"请求被别的请求（图片）挤占了"。三步打点其实已经摸到"派发延迟"这个层次，但没有时钟源取证，量不出"扣留"与"飞行"的区别。**该分支随后被搁置存档（未合入）。**

### 阶段 B：主线重开 + CDP 建设 + 第一次误判（13:03 – ~13:5x，分支 `perf/disable-artist-album-images`）

- **13:03:15** 从最新 main（`cb4cd37`，恰刚合入播放循环修复）重开调查分支；图片禁用改动以未提交形态重做（ArtistGrid/AlbumGrid）
- 尝试环境变量 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` 开调试端口 → **失败**（没进浏览器进程命令行）；改写入 `tauri.conf.json` → **成功**
- node-repl + `ws` 建立无头 CDP 通道（cdp3），可抓网络事件、console 事件、驱动页面滚动
- **踩坑①**：CDP 对 WebView2 自定义协议（ipc./lumo.localhost）**不报送 responseReceived/loadingFinished 完成事件**——曾把"没有完成事件"误读成"请求无限挂起"，后用 `img.complete` 证伪
- **踩坑②**：console 时间戳（纪元毫秒）与网络事件时间戳（单调秒）混算，对齐出一堆天文数字，修正时钟域后才有意义
- **洪泛实验**：200 并发冷 artwork 请求（cache-buster 绕缓存）期间，IPC 从 6ms 劣化到 707ms（100 倍）→ 向用户汇报"**图片确实是根因**"

> **误判 1：把"实验室里能复现该现象的充分条件"当成了"案发现场的必要条件"。** 洪泛机制本身是真的（artwork 与 IPC 共享协议处理管道），但用户场景里管道中一个 artwork 请求都没有。锚定效应形成：后面所有数据都先按"图片变体"解释了一遍。

### 阶段 C：用户证伪 + 重启复现（~13:5x – 14:05）

- 用户贴出前端/后端两套日志：图片已禁用，专辑分页仍 2651/5091/3150/4546ms，而后端仅 1.5-2.2ms——**"图片是根因"被正面证伪**，抛出那个定调的问题："从前端来看很慢，后端却非常快，为什么？"
- 顺带发现独立 bug：`library_get_lyrics` SQL 报 `no such column: t.primary_file_id`
- 用户重启 `npm run tauri dev`（端口 1420 冲突后由用户自己拉起），插桩配置随重启生效；用户实时滚动复现 1794-5668ms
- **14:05:47 – 14:06:36** 第一轮完整取证（DevTools 开着，物理滚轮 8 页），cdp3 全量捕获网络事件；用户贴出对应后端 ENTER/EXIT 日志

### 阶段 D：三视角对齐 → 第二次误判（14:0x – 14:2x）

- 对齐结果：POST 创建 → Rust ENTER 间隔 3 / 1782 / 4501 / 2158 / 4318 / 3709 / 4270 / 5573ms，与 AOP 总耗时逐条吻合 → 结论"延迟全在请求侧"
- 但请求侧的延迟被**归给了 wry/Tauri 分发管道**——还没意识到 requestWillBeSent 是渲染器"创建时刻"而非"上线时刻"
- 观察到自己无头驱动 ~147ms vs 用户 1.8-5.6s 的巨大反差，唯一显眼的差异变量是"用户 DevTools 开着" → **误判 2：DevTools 是 20-30 倍放大器**（又一次单变量归因，没做对照）
- **14:17:32** 无头 CDP 打好缓冲区标记，准备对照实验
- 记忆文件同步修正（图片论标记为已证伪）

### 阶段 E：对照实验打脸 + requestId 取证破案（14:21 – 14:40）

- **14:21:56 – 14:22:25** 用户关闭 DevTools 再滚 4 页：**5598 / 6088 / 6132 / 6727ms——更慢了**。误判 2 证伪
- 转而细看这轮 21 条网络事件，发现两个异常：
  1. OPTIONS 的 requestId 是 32 位 hex，POST 的是 `5548.x` ——**两种格式、两个签发方、两个时钟源**
  2. OPTIONS 比对应 POST 的"响应时刻"早 70-130ms 出现，且像"孤儿"
- 换算统一时钟（单调秒 + 固定偏移 1789866472.040，用 sent 事件校验恒定性）后真相浮现：
  - **OPTIONS 全部 2-10ms 往返**——管道在拥塞期间依然畅通
  - **POST 的 requestWillBeSent（渲染器创建）与 OPTIONS 真实上线之间差了 1.8-6.7 秒**——请求创建后根本没被放行
  - **铁证**：第 8 请求后端 ENTER=36.495 恰等于其 OPTIONS 响应时刻 36.495，放行到进 Rust 只隔毫秒
  - 旁证：空闲时的 `plugin:window|minimize` POST 全程仅 22ms
- **第三次修正**：不存在"wry 管道排队"；秒级延迟在**浏览器进程放行之前的调度扣留**（DevTools 所谓 Queueing）。wry/Rust 全链路无辜

### 阶段 F：两个决定性实验，结案（14:41 – 14:43）

同一实例、同一份 360-390 卡片 DOM，只差触发方式：

- **14:41:27 EXPB1**：程序化 `scrollBy(instant)` 触发翻页 → **132ms**
- **14:43:39 EXPB2**：程序化 `scrollBy(smooth)` 触发翻页 → **7985ms**（POST 创建后 7.9s 才放行）

→ 触发器是**滚动动画状态**（不经 OS 输入管线也能复现，排除"鼠标/输入"因素）。机制：Chromium 调度器在滚动动画期间为保输入/动画流畅而扣住渲染器新请求；330+ 张无虚拟化卡片的渲染补账把"安静期"拖后，造成 3ms → 6.7s 的递增恶化。无限滚动交互（滚到底才拉下一页）恰把每次请求投送到扣留窗口正中央。

### 阶段 G：沉淀 + 用户拍板"先验证再合并"（14:4x – 15:04）

- ~14:47 结案报告写入 `resources/doc/专辑艺人分页IPC队列延迟调查_2026-09-20.md`

## 四、复盘：为什么会走到岔路上

### 4.1 误判 1（图片是根因）——机制真实 ≠ 现场主因

洪泛实验是**真实的因果证明**，但证明的是"图片能造成排队"，不是"用户的排队来自图片"。锚点一旦立起，后续所有异常数据都被先按图片变体解释。**根因的证据标准应是：解释现场全部观测 + 移除后现象消失**；用户"禁图仍慢"的日志早在第一阶段就该做，而不是等用户自己贴上来。

### 4.2 误判 2（DevTools 放大器）——单差异变量归因

"我的会话快、他的会话慢，唯一显眼差异是 DevTools"——但显眼不等于隔离。真正差异是**驱动方式**（合成低频 vs 物理高频滚轮突发）。对照实验一小时后才做，其实五分钟就能证伪。

### 4.3 误判 3（wry 管道排队）——时间戳不查时钟源就对齐是危险的

requestWillBeSent 有渲染器/网络服务两种签发方（requestId 格式可分辨），"创建时刻"与"上线时刻"差值恰恰就是本案的延迟本体。**跨层日志对齐前，先问每个时间戳"谁打的、什么时候打的、什么语义"。**

### 4.4 工具语义的误导链

DevTools 把调度扣留标成 "Queueing"（暗示资源排队）→ Tauri 把 IPC 伪装成 fetch（暗示普通网络请求、接受 web 调度策略对待）→ "本地 IPC"没有任何优先级特权。**抽象层不会告诉你它借用的基础设施对你的请求做了什么决定。**

### 4.5 最终有效的三板斧（按贡献排序）

1. **三视角时间戳对齐**（console / CDP / 后端 ENTER）——把黑盒切成三段
2. **requestId 时钟源取证**——在同一份 CDP 数据里挖出"两种证人"
3. **同实例控制变量法**——instant vs smooth 一次对比直接结案，所有存量假说一次筛死
