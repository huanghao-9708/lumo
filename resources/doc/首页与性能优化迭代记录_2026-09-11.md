## 三、性能优化（本轮重点）

### 3.1 SQL 改写：先 ID 子查询，再 LEFT JOIN（第三轮）

**问题**：首页排行榜的原 SQL 在真实库（32k 曲）上实测：

| 查询 | 原耗时 |
|---|---|
| 播放最多的歌曲（`ranked_query WHERE play_count > 0`） | 6700ms |
| 听得最多的歌手 | 9000ms |
| 播放最多的专辑 | 6700ms |

**根因**（`EXPLAIN QUERY PLAN` 实证）：`ranked_query` 的 SELECT 里有 4 个相关标量子查询（主艺人 id、艺人 GROUP_CONCAT、source kind 等），`WHERE play_count > 0` 触发全表扫描时，每个子查询都对每行执行一次 → 30k 行 × 4 子查询 ≈ 12 万次主键查找。`OR` 形态的 WHERE 还会让 planner 放弃索引。

**改写模式**（两步法）：

```sql
-- 第一步：只拿 ID（命中索引，毫秒级）
SELECT t.id FROM tracks t
WHERE t.play_count > 0
ORDER BY t.play_count DESC, t.id ASC
LIMIT ?;

-- 第二步：拿 ID 集合后，再 LEFT JOIN 拼完整列
SELECT t.id, t.title, ..., al.cover_artwork_id
FROM tracks t
LEFT JOIN albums al ON t.album_id = al.id
JOIN media_files m ON m.id = COALESCE(t.primary_file_id, (SELECT ...))
LEFT JOIN favorite_tracks ft ON t.id = ft.track_id
WHERE t.id IN (?, ?, ...)
ORDER BY t.play_count DESC, t.id ASC;
```

歌手榜/专辑榜同理：先聚合出 Top N 的 ID（此时 `SUM` 是聚合键，数学上与逐 ID 重算等价），再逐 ID 补齐展示列。

**改写后实测**（同真实库）：

| 查询 | 原 | 改写后 | 倍率 |
|---|---|---|---|
| Top Track | 6700ms | 4ms | ~1600× |
| Top Artist | 9000ms | 1ms | ~9000× |
| Top Album | 6700ms | 4ms | ~1600× |
| 8 个查询合计 | 90ms+ | ~6ms | ~15× |

**等价性核对**：用 Python 内置 sqlite3 以只读模式打开真实库，对 Top Track（30 条）、Top Artist（19 条）、Top Album（25 条）逐项比对 `(id, play_count)`，原版 vs 改写版全部一致。

**方法沉淀**：`cargo check` 只能证明 Rust 编译过，**证明不了 SQL 列名/表名/语义正确**。任何新写或改写的 SQL，都应在真实库上用 Python 内置 sqlite3（`file:...?mode=ro` 只读打开）原样跑一遍核对。

### 3.2 Tauri 命令线程模型：Rust 主线程串行（第三、六轮）

**Tauri v2 事实**（官方文档确认）：默认 `#[tauri::command]` + `pub fn` 跑在**主线程**且**串行执行**——即使 JS 端用 `Promise.all` 并行触发，Rust 端也是排队一个个跑。

**修法**：`#[tauri::command(async)]` 属性宏 + 保持 `pub fn`（**不是** `pub async fn`）。Tauri 会把命令体移到 tokio blocking pool，并发执行，不阻塞其他 IPC。

> 本项目惯例：**用 `#[tauri::command(async)]` 属性宏，不用 `pub async fn`**。后者需要显式依赖 tokio crate 并自行处理 `State` 生命周期，仅在需要 `tokio::spawn` 的场景（见 3.3）才用。

**已 async 化的命令**（`commands/library.rs`）：

- 第三轮：`library_get_insights`（首页 8 个聚合查询串行 90ms，会冻结 UI）。
- 第六轮（用户报列表接口 5s 后）：`library_get_albums` / `library_get_album_count` / `library_get_artists` / `library_get_album_tracks` / `library_get_artist_albums` / `library_get_artist_album_count` / `library_get_artist_tracks`。
- 保持 sync 的：`library_get_album_by_id` / `library_get_artist_by_id` / `library_get_artist_stats` 等详情类命令——用户主动点击触发，不存在批量并行堆积。

**原则**：所有 list-load 类命令（切 tab / 首屏会并行触发的）都应 async 化；单条详情类可以保持 sync。

**注意**：SQL 本身实测只 0.3-15ms，async 化的真正收益是**消除主线程排队**，让并行 IPC 真的并行——不是让单条变快。

### 3.3 WebView HTTP 6 并发上限与封面拉取后台化（第七轮，本轮最深的坑）

**现象**：async 化后用户仍报"队列等待 15s"。

**真凶**：Tauri v2 **dev 模式**的 IPC 走 `http://ipc.localhost`，受 **WebView2（Chromium 内核）HTTP/1.1 单 host 6 并发上限**约束。release 模式走原生 IPC 通道（named pipe / stdio），不受此限。

`library_fetch_missing_album_cover` / `library_fetch_missing_artist_cover` 走 iTunes API + 下载 600×600 图，单次 2-10s。前端虽然 fire-and-forget 调用（不 await），**但请求本身已占住一个并发坑位**。浏览时点开 5+ 个无封面的专辑/艺人 → 5+ 个并发长请求挂着 → 其他所有列表 IPC 全部 Stalled 在 WebView 队列里等 5-15s。

**教训**：async 化解决的是 Rust 端主线程串行；**解决不了 WebView 端的 6 并发上限**。两层问题必须分开处理。

**修复**（完全脱离 IPC channel）：

1. **命令体立即返回**：`library_fetch_missing_album_cover` / `library_fetch_missing_artist_cover` 校验隐私开关后，1ms 内 `return Ok(None)`。
2. **真实下载后台跑**：`let pool = db_state.db.clone();`（`DbPool` 内部是 Arc，Clone 后 `'static`）+ `tokio::spawn(async move { ... })` 执行 iTunes 查询、图片下载、缩略图生成、写 DB。原实现整体抽为 `fetch_album_cover_impl` / `fetch_artist_cover_impl` 私有函数。
3. **完成通知**：`app.emit("album-cover-fetched" | "artist-cover-fetched", CoverFetchedEvent { target_id, artwork_id })`（payload 模型在 `models.rs::CoverFetchedEvent`）。
4. **前端订阅**：`stores/player.ts` 的 `initEventListeners()` listen 两个事件，更新 `albums` / `artists` / `currentAlbumDetailsData` / `currentArtistDetailsData` 中对应条目的封面 id。原 `.then(newCoverId => ...)` 路径因命令恒返回 `None` 自然失效，由事件回调接管。
5. **依赖**：`Cargo.toml` 新增 `tokio = { version = "1", features = ["rt", "macros"] }`（reqwest 0.13 自带 tokio 但不对外暴露）。

**代码模式**（供后续类似的"长任务命令"复用）：

```rust
#[tauri::command]
pub async fn library_fetch_missing_album_cover(
    app: tauri::AppHandle,
    db_state: State<'_, DbState>,
    album_id: i64,
    allow_online: Option<bool>,
) -> Result<Option<i64>, AppError> {
    if allow_online != Some(true) { return Ok(None); }

    // State<'_, DbState> 有生命周期，不能 move 进 spawn；
    // DbPool 是 Arc，clone 后 'static。
    let app_clone = app.clone();
    let pool = db_state.db.clone();
    tokio::spawn(async move {
        match fetch_album_cover_impl(&app_clone, &pool, album_id).await {
            Ok(Some(artwork_id)) => {
                use tauri::Emitter;
                let _ = app_clone.emit("album-cover-fetched",
                    CoverFetchedEvent { target_id: album_id, artwork_id });
            }
            Ok(None) => {}
            Err(e) => tracing::warn!("[cover] album={} fetch failed: {}", album_id, e),
        }
    });

    Ok(None) // 立即返回，不占 WebView 并发
}
```

**设计原则**：任何**耗时超过 100ms 或涉及网络/文件 IO** 的命令，都不应同步占用 IPC channel——要么 `#[tauri::command(async)]`，要么 `tokio::spawn` + 事件通知。

## 四、Bug 修复

### 4.1 时间戳时区偏移（第二轮顺带修复）

**问题**：后端 `tracks.last_played_at` / `play_history.played_at` 由 SQLite `datetime('now')` 写出，是 **UTC 朴素串**（如 `2026-09-11 01:19:51`，无时区标记）。前端 `new Date("2026-09-11 01:19:51")` 会被浏览器按**本地时区**解析——GMT+8 下整整偏 8 小时。`RecentlyPlayed.vue` 原来直接 `new Date(playedAt)`，"今日/昨日"判断会错。

**修复**：新增 `src/utils/datetime.ts`，`parseDbTime` 对无时区标记的串补 `Z` 再解析；`formatPlayedAt`（今日/昨日/日期）与 `formatRelativeTime`（相对时间）统一走它。`RecentlyPlayed.vue` 删除本地实现改为引用。

**约定**：**任何地方都不要直接 `new Date(dbTime)`**，一律走 `utils/datetime.ts`。

### 4.2 `library_get_playability` 列名错误（第五轮）

**报错**：`Database error: no such column: m.path in SELECT t.id, m.id, s.kind, s.root_uri, m.path ...`（`http://ipc.localhost/library_get_playability`）。

**根因**：`media_files` 表**没有 `path` 列**（共 24 列，含 `relative_path` / `normalized_path` / `file_name`）。业务上的"完整路径" = `s.root_uri || '/' || mf.relative_path`（其他命令如 `library.rs:424/909` 均如此拼）。`library_get_playability` 误写 `m.path`。

**修复**：`commands/library.rs` 一行修改 `m.path` → `m.relative_path`，与下游 `Path::new(&root).join(p)` 语义完全一致（`p` 即相对路径）。

**验证**：Python 只读复现原报错 → 改后同一 chunk 跑通，local 歌曲路径拼接正确且 `exists()==True`；500 条 chunk 实测 0.7ms。

**约定沉淀**：写涉及 `media_files` 路径的新 SQL 时，**`path` 列不存在**，用 `relative_path` 与 `root_uri` 拼接。

## 五、IPC 性能诊断工具链（本轮形成）

排查 5s/15s 问题过程中，本项目形成了三层诊断手段：

1. **`ipc_trace!` 宏**（`src/ipc_trace.rs`，已有）：每个 `#[tauri::command]` 入口一行 `let _trace = ipc_trace!("cmd_name");`，RAII guard 在 drop 时打印 `[IPC] ← cmd EXIT seq=N backend=Xms`。**这条日志能区分"SQL 慢"还是"IPC 排队"**：backend < 50ms 而前端看到 5s = 排队问题；backend > 500ms = SQL/IO 真慢。慢调用（>100ms）自动升 WARN 级别。
2. **Python 实跑 SQL**：`python -c` 或临时脚本，`sqlite3.connect(f"file:{DB}?mode=ro", uri=True)` 只读打开真实库，逐条跑 SQL 计时 + `EXPLAIN QUERY PLAN` 看扫描方式。注意 PowerShell 工具不回传 stdout，输出要 `Set-Content -Encoding UTF8` 落文件再读。
3. **WebView dev tools Network 面板**：`http://ipc.localhost/...` 请求的 Stalled/Queueing 时间反映 WebView 6 并发排队；Waiting (TTFB) 反映 Rust 端真实处理时长。

## 七、经验教训沉淀

1. **编译通过 ≠ SQL 正确**。任何 SQL 改动必须在真实库上实跑（Python sqlite3 只读模式）验证列名、语义与等价性。
2. **`OR` 是 SQLite 索引杀手**。WHERE 含 OR 时 planner 常放弃索引全表扫；用"先 ID 子查询再 LEFT JOIN"两步法绕过，对相关标量子查询尤其有效。
3. **Tauri v2 性能问题分两层，缺一不可**：
   - **Rust 端**：默认 sync 命令在主线程串行 → list-load 类命令用 `#[tauri::command(async)]`；
   - **WebView 端**：dev 模式 IPC 走 HTTP，6 并发上限 → 网络/IO 长任务用 `tokio::spawn` + `app.emit` 事件，命令体立即返回。
   - "fire-and-forget"的前端调用**不等于**不占并发——请求本身就占坑位。
4. **`State<'_, DbState>` 不能 move 进 `tokio::spawn`**（非 `'static`）；内部 `DbPool` 是 Arc，`clone()` 后即可。
5. **DB 时间戳是 UTC 朴素串**，前端解析一律走 `utils/datetime.ts`，禁止裸 `new Date(dbTime)`。
6. **`media_files` 无 `path` 列**，完整路径 = `root_uri` + `relative_path` 拼接。
7. **UI 里禁止硬编码版本号/介绍文案**，统一走 `src/config/appInfo.ts`；发版只改 `package.json`。
8. **诊断三板斧**：`ipc_trace!` 后端日志（区分 SQL 慢 vs 排队）→ Python 只读实跑 SQL（列名/语义/耗时/查询计划）→ WebView Network 面板（Stalled vs TTFB）。
9. **本机工具链注意事项**：Bash 工具链损坏（改用专用文件工具 + PowerShell）；PowerShell 不回传 stdout（输出落文件再读，须 `Set-Content -Encoding UTF8`）；RustRover 占句柄时 Edit 可能 `EBUSY` 或静默丢失（改完 Grep 复核 + 类型检查兜底）。

## 八、遗留事项与后续建议

1. **release 模式复测**：WebView 6 并发限制只在 dev 模式存在，release 走原生 IPC。建议打一次 release 包对比启动速度，确认 dev 侧优化在 release 的表现。
2. **启动 IPC 合并（可选）**：App.vue 启动仍并行触发 8-10 个 IPC。虽然已 async 化 + 不再有长任务占坑，但进一步可做 `library_get_startup_bundle` 一次拿回全部启动数据，把 IPC 数从 ~10 降到 1-2。
3. **`.scrollbar-always` 场景确认**：目前无使用方。若歌词/设置页需要常驻滚动条，给容器加此类即可。
4. **`ranked_query` 的 IN 参数上限**：SQLite 默认变量上限 999，当前 LIMIT 5~50 安全；若未来榜单扩到数百条需分批。
5. **冷灰渐变清理（历史遗留）**：artist 头像占位的 `from/to-gray-*` 14 处待 LDL 暖色中性阶梯注册后统一替换。
