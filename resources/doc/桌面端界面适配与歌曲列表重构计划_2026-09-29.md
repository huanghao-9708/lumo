# 桌面端界面适配与歌曲列表重构计划

> 日期：2026-09-29  
> 状态：待实施  
> 范围：Lumo 桌面端；共享数据契约变更需验证移动端  
> 决策来源：默认窗口 1200×720、移除侧栏数字、丰富歌曲信息、统一各模块列表规则

## 1. 目标与完成标准

本轮目标是在较小的桌面窗口中保持舒展、清晰、可操作的音乐浏览体验，同时让歌曲信息可按需展开。具体完成标准：

1. 新安装或无历史窗口状态时，默认打开为 **1200×720 CSS/逻辑像素**；建议最小可调整至 **1024×640**，前提是该尺寸的布局验收全部通过。窗口尺寸不得超出当前显示器可用工作区；记住用户主动调整后的尺寸，并在显示器变化时重新约束。
2. 左侧导航及自建歌单行不显示尾部数量；页面标题下方、详情页和有业务含义的统计区域仍可显示数量。
3. 所有桌面歌曲列表使用相同的表头、列宽、行态、操作入口和尺寸规则；页面可以按上下文隐藏冗余列。
4. 默认视图在 1200×720 下能完整阅读歌曲标题、艺术家、专辑、时长和音频信息；年份、流派、文件大小等通过可配置列与“详细视图”提供。
5. 歌曲规模较大时，滚动、分页和播放操作不因新增列而出现明显退化；空数据、缺失标签与多音源的展示准确。

本计划只定义重构工作和验收，不在此文档中宣称功能已实现。

## 2. 当前基线与问题

| 位置 | 当前状态 | 对本轮的影响 |
|---|---|---|
| `src-tauri/tauri.conf.json` | 默认 1600×900，最小 1280×720 | 首次打开窗口偏大，无法检验小窗口布局 |

| `SidebarLeft.vue` | 多个导航项与每个自建歌单显示数量 | 文字与数字争夺侧栏宽度，视觉噪声较多 |

## 3. 设计决策

### 3.1 窗口与空间

- 默认尺寸定为 **1200×720**。启动时按显示器可用工作区限幅；若工作区小于默认值，优先保证整个窗口可见。
- 最小尺寸目标为 **1024×640**。先完成布局后再下调窗口配置中的 `minWidth/minHeight`，避免用户能缩到功能不可用的状态。
- 保持桌面 UI 的文字可读性，不做整页等比缩放。优先压缩非核心留白和装饰，再按容器宽度调整列、图片和次要控件。
- 左侧栏目标宽度从 240px 调整到约 **216–224px**，以实际中文标签、长歌单名称和窗口控制测试结果定稿；不能仅靠裁切内容达标。
- 底部播放栏目标高度约 **88–96px**。优先保留播放/暂停、切歌、进度和当前曲目信息；音量与次级输出控件可在窄窗口内收纳。不得为了省空间缩小关键按钮的可点击区域。
- 右侧 Inspector 在 1200px 及以下默认收起。用户主动打开时作为覆盖内容区的面板，并提供清楚的关闭入口；不要让面板长期遮住列表操作列。
- 内容区布局以**实际容器宽度**决定列显示和网格列数，不再单纯使用浏览器视口的 `sm/md/lg` 判断。

### 3.2 字体、按钮与图片

| 元素 | 1200×720 目标 | 较窄/较矮窗口处理 |
|---|---|---|
| 页面标题 | 约 28px，保留清晰的标题与元数据层级 | 标题换行或截断时不能覆盖工具栏；详情标题允许两行 |
| 歌曲正文、侧栏正文 | 保持约 13px 的当前阅读基准 | 不通过缩到 10–11px 来换取更多列 |
| 元数据、表头 | 约 11–12px；数字等宽对齐 | 对比度和可读性优先于装饰性小字 |
| 图标按钮 | 图标约 14–18px；桌面点击区域至少 32×32px | 收纳低频按钮，而不是继续缩小点击区域 |
| 主播放按钮 | 约 42–46px 的可见尺寸 | 保持醒目且不与进度条、音量重叠 |
| 底栏封面 | 约 44–48px，保持正方形 | 曲名空间不足时截断，不压缩封面比例 |
| 专辑/艺人详情封面 | 1200 窗口约 144–160px | 低高度窗口可进一步缩至约 120–136px，文本区仍能完整操作 |
| 专辑/艺人网格 | 依内容区宽度自动决定列数 | 调整卡片最小宽度与间距，避免出现过窄的卡片或水平滚动 |

以上是实施目标值，不是逐组件硬编码清单。将常用尺寸与紧凑布局断点纳入设计 token；先检查 `HomeView`、详情页、搜索页、沉浸播放页、弹窗及左右侧栏，再统一调整。

### 3.3 侧栏数字

- 移除一级导航、收藏分组及自建歌单行右侧的数字，包括用于显示的 `count` 字段映射和模板节点。
- 页面内原有的曲目数、专辑数等概览继续承担统计信息展示。不要仅为了侧栏显示而新增计数查询；移除侧栏数字本身也不应被表述为显著的性能优化，因为启动数据仍被页面使用。
- 侧栏行以图标、名称、选中态为主要信息；长名称使用省略和完整名称提示，保证无数字后仍整齐对齐。

### 3.4 歌曲列和信息层级

| 字段 | 标准视图 | 详细视图 / 自选列 | 数据规则 |
|---|---|---|---|
| 标题 | 必显 | 必显 | 长标题省略，悬停/聚焦可看全名 |
| 艺术家 | 通常显示 | 可配置 | 艺术家详情可省略本列 |
| 专辑 | 通常显示 | 可配置 | 专辑详情可省略本列 |
| 时长 | 显示 | 可配置 | 数字右对齐，缺失时显示 `—` |
| 音频信息 | 显示一列 | 可配置 | `FLAC`、`MP3 · 320 kbps`；仅依据真实元数据生成，不以扩展名推断采样精度 |
| 年份 | 不默认显示 | 可选 | 优先歌曲年份；没有时可用专辑发行年份，来源需在数据层明确 |
| 流派 | 不默认显示 | 可选 | 多流派需定义截断和完整查看方式；无标签时显示 `—` |
| 文件大小 | 不默认显示 | 可选 | 显示当前首选音源的大小；多音源切换后应对应当前文件 |
| 播放时间等场景字段 | 所在页面显示 | 页面专属 | 最近播放保留播放时间，不被通用列设置移除 |

- 标准视图优先保证内容阅读；“详细视图”开启年份、流派、大小等列，必要时允许横向滚动，但固定标题/操作信息并明确滚动提示。用户可在表头的“显示列”菜单单独增减可选列，并将选择保存在本机。
- 在较窄容器中，按“流派 → 大小 → 年份 → 音频信息 → 专辑”的次序收纳可选信息；标题、播放入口始终保留。用户主动选择的列优先级高于默认列，但无法同时容纳时提供横向滚动，不悄悄丢失用户选择。
- 列宽由同一列定义驱动表头和歌曲行；不再逐页复制不同的 `flex` 与 `hidden` 类。数字列右对齐，文本列左对齐，图标操作区宽度固定。
- 音质标签只描述能够验证的事实：有比特率显示 `320 kbps`，有位深和采样率时才显示 `24-bit / 96 kHz`；缺失则省略，不擅自标“无损”或“Hi-Res”。

## 4. 数据补齐方案

1. **字段契约**：在 Rust `TrackDTO`、前端 `TrackDTO/Track` 中补充可空的年份、流派、比特率、采样率、位深；文件大小及格式沿用现有字段。需要明确这些字段描述的是歌曲还是当前首选媒体文件。
2. **扫描与入库**：扩展 `AudioMetadata` 标签提取和 `LibraryService::index_file`，解析歌曲/专辑年份、流派及可获取的音频属性；处理空标签、异常年份、复数流派、同一歌曲多个文件和重复扫描。当前数据库已有相关列/表，但需核实迁移与旧库升级路径，禁止覆盖用户已有的有效值。
3. **列表查询**：一次分页查询返回列表必需的轻量字段；流派聚合须避免一对多连接造成歌曲重复或分页错乱。不要在每一行渲染时额外发一次 IPC 或读文件。
4. **旧曲库**：新字段默认可空；提供增量补扫路径，不要求用户清空曲库。补扫前后列表都能正常显示。
5. **多音源**：音频信息和大小跟随首选/当前播放文件；如果某页面只持有首选文件元数据，显示文案不得暗示所有版本都具有相同音质。

## 5. 共用列表架构

建议拆成三层，以逐页迁移降低回归范围：

1. **列定义与格式化**：集中定义字段标识、标签、默认宽度、优先级、上下文可见性、空值与音质/大小/年份格式化。表头和行共用同一份列配置。
2. **列表外壳**：负责表头、容器宽度测量、滚动、加载/空/错状态、可选列菜单和用户偏好；支持普通列表、分页与虚拟列表的数据源。
3. **歌曲行**：负责序号/正在播放、收藏、多选、标题/艺人/专辑跳转、双击播放、不可播状态及更多操作。页面通过配置传入专属操作和字段，不在共用组件里堆页面名称判断。

保留各页面的真实业务差异：队列顺序与过滤后原始索引、歌单删除、专辑曲序、最近播放时间、文件夹大小、搜索分页、AI 歌单等。先完成基线和标准行，再分批迁移，迁一页验一页。虚拟列表继续使用固定行高；若引入双行标题，必须同步修改虚拟列表高度计算。

## 6. 实施阶段与交付物

| 阶段 | 工作 | 交付与验收点 |
|---|---|---|
| P0：布局基线 | 记录当前截图、窗口尺寸、缩放比例及关键交互；建立页面清单和断点检查表 | 形成可对照的 1200×720、1024×640、1600×900 样本 |
| P1：窗口与紧凑布局 | 改默认尺寸；处理工作区限幅/记忆；调整侧栏、播放器、标题、封面、网格、Inspector 与弹窗 | 目标尺寸无裁切、重叠和不可达按钮；大窗口仍舒展 |
| P2：侧栏净化 | 删除导航和歌单行尾计数，调整长名称与选中态 | 所有侧栏分组对齐，页面统计入口保留 |
| P3：共用列表基础 | 建立列定义、共用表头/歌曲行及列偏好；先迁移全部歌曲、收藏、最近播放 | 三处行为一致；原有播放、选择、收藏、滚动功能通过回归 |
| P4：扩展所有模块 | 迁移队列、歌单、智能歌单、专辑/艺人详情、文件夹、搜索、AI 歌单及适用的首页歌曲区 | 各页面只保留必要差异，同一字段样式一致 |
| P5：元数据与详细视图 | 补提取、入库、查询和前端字段；上线标准/详细视图、显示列菜单 | 有标签显示准确，缺失显示 `—`；旧曲库可增量补扫 |
| P6：规范与发布验收 | 更新 LDL v2 的空间、字阶、侧栏项、歌曲行、播放器规范；清理旧实现 | 设计文档与代码一致，完成矩阵测试和性能对照 |

P3 与 P5 的接口可提前设计，但不要在数据未准备好时推出大量空列。每阶段均可独立评审，不必等全部模块一次性替换。

## 7. 验收矩阵

### 7.1 视觉与可用性

- **尺寸**：1024×640、1200×720、1366×768、1600×900；各尺寸检查 100%/125%/150% 系统缩放，并确认窗口处于可用工作区内。
- **主题**：亮色、暗色；检查标题、元数据、悬停、选中、正在播放、禁用状态。
- **内容**：极长中英文歌名、长艺术家/专辑名、无封面、无标签、多流派、未知格式、多音源、大量歌单、空列表。
- **交互**：窗口缩放、侧栏长名称、Inspector 开关、沉浸播放、搜索、排序/筛选、多选、双击播放、键盘焦点、分页/无限滚动、弹窗。
- **布局红线**：无水平整页滚动、按钮遮挡、文字覆盖、表头与行错位；保留足够的标题阅读宽度，任何主要操作可通过鼠标或键盘到达。

### 7.2 功能与性能

- 共用列表迁移前后，播放队列顺序、搜索结果定位、收藏状态、不可播提示、批量操作和滚动位置一致。
- 大曲库滚动与分页使用原有虚拟化/分页机制；新增字段不触发逐行 IPC。对照 P0 样本记录首屏时间、列表滚动流畅度、分页耗时、查询条数及内存变化；出现可感知退化时先定位查询或渲染原因再合并。
- 前端执行 `npm run typecheck`、`npm run test:unit`、`npm run build`；后端执行相关 Rust 测试。测试重点覆盖列配置/持久化、格式化、元数据入库、分页聚合、多音源与缺失值，而不是重复断言静态模板。
- Android 不采用本轮桌面尺寸，但共享 DTO、扫描和数据查询变更须通过移动端主要歌曲列表回归。

## 8. 风险与处理

| 风险 | 处理方式 |
|---|---|
| 1200 宽度同时展示太多列 | 标准/详细视图区分，依据内容区宽度排布；用户指定列时提供横向滚动 |
| 1024×640 的底部控制与主列表互相挤压 | 优先精简次级控件及纵向留白，保持播放主操作和可读字号 |
| 元数据标签缺失或来源不一致 | 字段保持可空，明确歌曲/专辑/媒体文件来源；无值显示 `—` |
| 流派关联使分页结果重复 | 查询中先聚合流派，再对歌曲分页；验证总数和排序稳定性 |
| 多处列表一次改动过大 | 共用组件逐页迁移，每页完成视觉及行为回归后继续 |
| 旧 LDL 规范与实现冲突 | P6 同步修订 `resources/ui/lumo_design/v2/`，删除旧断点与计数规则 |

## 9. 建议实施顺序

先完成 **P0 → P1 → P2**，让 1200×720 成为可信的设计基线；随后做 **P3/P4** 统一列表；最后完成 **P5** 的丰富信息与 **P6** 的规范、性能验收。实施时以本计划的用户决策为准；具体像素值允许依据验收样本微调，但不能以压低正文可读性来换取列数。
